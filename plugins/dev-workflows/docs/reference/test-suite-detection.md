# Test suite detection

`test-baseliner` is the agent `/implement`, `/upgrade` and `/vuln` run — directly, or through `upgrade-executor` and `vuln-fixer` — before a change to record what already passes, and again afterwards to diff against that record. It finds your test suites by scanning for **markers** — a file whose presence names a build system — and the set of markers it knows is a table in the agent's own `capture` step 1. **That table is the coverage**: a suite runs because its marker is a row, and a build file the table does not list detects nothing on its own. This page publishes the table so you can answer "is my technology covered?" without opening an agent file, and says what happens when the answer is no — which is a reported outcome rather than a failure.

## The detection table

Eleven rows, over fourteen distinct markers (two of them globs). `Gemfile` is the one marker that appears in two rows, one per Ruby test framework; the other rows take a marker each, several of them with alternative names. A marker becomes a **candidate** only where its own qualifier holds.

| Marker | Framework | Qualifies when | Command |
|---|---|---|---|
| `pom.xml` | Maven | always | `./mvnw test -q` (falls back to `mvn test -q` with no wrapper) |
| `build.gradle` or `build.gradle.kts` | Gradle | always | `./gradlew test` (falls back to `gradle test` with no wrapper) |
| `Gemfile` | RSpec | `spec/` exists | `bin/rspec --format documentation` (falls back to `bundle exec rspec --format documentation` with no binstub) |
| `Gemfile` | minitest | `test/` holds a `*_test.rb` or `test_*.rb` file other than `test_helper.rb`, or `Rakefile` declares a `test` task | `bin/rails test -v` where `bin/rails` exists, else `bundle exec rake test TESTOPTS=-v` |
| `Package.swift` | SwiftPM | always | `swift test` |
| `*.xcodeproj` or `*.xcworkspace` | Xcode | no `Package.swift` beside it — a package with a checked-in or generated project is one body of tests, and `swift test` is its pinned entry point | `xcodebuild test -scheme <scheme>`, the scheme read from `xcodebuild -list` |
| `go.mod` | Go | always | `go test ./... -v` |
| `Cargo.toml` | Cargo | always | `cargo test`; with a `[workspace]` table, one `cargo test -p <name>` per default member |
| `package.json` | Jest/npm | `scripts.test` is present and is not the `npm init` placeholder (`no test specified`), or a `workspaces` field is present and some workspace's own `package.json` has one | `CI=true npm test`; with a `workspaces` field, one `CI=true npm test --if-present --workspace <name>` per qualifying workspace |
| `pyproject.toml`, `setup.py`, or `pytest.ini` | pytest | always | `pytest -v` |
| `Makefile` | Make | a `test` target exists | `CI=true make test` |

Where a tool ships a pinned entry point, that is the command: `./mvnw`, `./gradlew`, and Ruby's `bin/` binstubs ahead of `bundle exec`. A JavaScript command carries `CI=true` because several runners watch for file changes outside CI, and a watcher never returns; two runners do not read `CI` and are given their own single-run flag instead (`karma start … --single-run`, `ng test … --watch=false`), rebuilt from the invocation rather than appended to the script's text.

## How the scan reads that table

The scan reads **every** marker and never stops at the first — first-match-wins is what once made a Rails application carrying an asset-build `package.json` report a JavaScript baseline for a Ruby suite. It is rooted at the project root the caller names, descends into that root's subdirectories so that a front end in its own directory is a suite of this repository, and prunes `node_modules/`, `vendor/`, `target/`, `build/`, `dist/`, `out/`, `coverage/`, `.git/`, `.gradle/`, `.venv/` and `venv/` wherever they occur — measured, an unpruned scan returned five markers where two were real, one of them a dependency's own `package.json` that qualifies under the table's rule.

Where two qualifying directories of one row sit side by side, neither containing the other, they are two suites and **both run**. Where one contains another of the same row, only the outer is a candidate and the inner is named in the return's `### Notes`, because the containing command usually recurses over it — a Maven or Gradle reactor, `pytest`'s own discovery — and running both would sum the same tests twice; where it does not recurse, that note is marked `CAVEAT: `, because there a qualifying suite genuinely went unrun. Two kinds of candidate are split further rather than run as one: a `package.json` carrying a `workspaces` field becomes one suite per workspace with its own test script, and a `Cargo.toml` carrying a `[workspace]` table becomes one suite per default member. A `Makefile` whose `test` recipe drives another candidate's runner is a wrapper and not a rival — that candidate runs through `CI=true make test`, the project's own pinned entry point, and is parsed with its own framework's patterns.

## More than one suite

A repository holding a Rails suite and a JavaScript one, or a Java suite and an Angular one, has two real test suites, and a baseline taken from one of them cannot detect a regression in the other. So **every candidate the scan resolves to a suite is baselined**, each from **its own run directory** — the directory its qualifying marker sits in, for an ordinary suite — and each under **its own copy of the ten-minute bound**, so a slow suite cannot truncate a later one. With no test command supplied they run in the table's own row order, and within one row in their marker paths' lexicographic order, so the same repository yields the same order on every run.

The return reports **per suite**. `Framework` and `Command` are comma-separated lists in run order, a name repeating where the run holds more than one suite of it, and a `### Suites` section carries one line per detected suite: the framework, the marker that qualified it as a path relative to the scan root, the command, that suite's own status (`OK`, `RUN_FAILED`, `NO_TESTS` or `not run`) and its own counts. The run-level `Status` is one value computed from the set — `PARTIAL` where at least one suite produced counts and at least one did not, which is incompleteness rather than a verdict on your code. Every test identifier carries a prefix naming its suite — the framework alone where that framework names one suite, the framework plus that suite's marker path where it names several — so two suites cannot mint the same identifier and mask each other's loss. What the prefix does not separate is what a `Make` fold puts *inside* one suite: several candidates print into one output under one prefix, which is the first of the known limits below.

## A stack the table does not list

PHP, .NET, Scala, Elixir, Dart and C++/CTest have no marker in the table, so nothing in such a repository qualifies **on its own build files**. Two things can still give it a suite, and both are worth checking before concluding it has none: a `Makefile` with a `test` target qualifies regardless of what the recipe drives, which is the table's one stack-agnostic row — its output is parsed best-effort for `X passed` / `X failed` / `X pass` / `X fail`, and where no pattern matches the counts are 0 and a note says so — and any other marker the repository happens to carry, such as a `package.json` with a real test script, qualifies on its own terms.

Where nothing qualifies, **that is not a failure and it is not silent.** With no candidate and no supplied command, the agent runs nothing and returns its normal structure with `Status: COMMAND_NOT_FOUND`, `Framework: not detected`, every count 0, and a `### Notes` line saying no runner was found. It does not fail the call.

`/implement` acts on that status at Pre-Phase 3.5 — after the branch is cut and **before any file is edited**, which is the last point at which the answer can still be a baseline rather than a test run. It surfaces the block's `### Notes` and `### Suites` first, then asks: *Specify test command to use*, *Skip tests for this run*, or *Cancel*. A command you supply is recorded, the capture is re-dispatched immediately with it, and that same command is carried on every later `test-baseliner` call in the run, because a verify over a different set of suites is not a comparison. A skip is written into the Phase 5 report's `### Deferred items` with its reason. `/upgrade` and `/vuln` reach the same question at the same point — after the capture and before anything is edited — and each asks it once for the whole run, because each captures once for the whole run. A command you supply is carried forward the same way in all three, onto every later call — including the verify each of these two runs inside its own agent. Their middle option differs from `/implement`'s in what it commits you to: there is no work to skip in a dependency bump, so it applies the change unverified and every pull request the run opens is a draft carrying a DO-NOT-MERGE line. [`/vuln`'s page](../commands/vuln.md) records what its two paths did before they were made to agree.

A supplied command is the coverage a repository has until its stack is a row. It becomes the run set, one suite per command; a command that matches no detected suite is a suite of its own, its framework the runner the command names or `hinted` where it names none, and its `### Suites` marker reads `command_hint#<n>` for its position in what you sent. Detection still runs underneath — a supplied command narrows what is **run**, never what is **detected** — so any suite it leaves out still gets a `### Suites` line, marked `not run`. Read that section after supplying a command: that is what it is there for.

## What adding a technology takes

The coverage is a table, and the machinery around it is general. Adding a technology is **two rows**:

1. A row in `capture` step 1's detection table — the marker, the framework it selects, the qualifier that turns the marker into a candidate, and the command. The command carries whatever verbosity flag that runner needs, because the parse also collects each passing and failing test's identifier out of the same output.
2. A row in `capture` step 3's parse table — the patterns that runner's output prints its passing, failing and skipped counts in. That table has ten rows today, SwiftPM and Xcode sharing one.

Everything between those two tables is written against a row rather than against a framework, and a new row inherits all of it: the rooted, pruned scan; the containment rule; the per-suite run directory and the per-suite bound; the suite prefix on every identifier; the one `Status` computed from the set; and the pairing a `verify` call does against the baseline's `### Suites` rows.

What is **not** general is worth knowing before writing a row, because each of these was written for one ecosystem's shape: the `CI=true` prefix and the two-runner watch carve-out are JavaScript's, the `workspaces` and `[workspace]` divisions are npm's and Cargo's, and the wrapper rule is `Make`'s. A runner that watches for file changes by default needs a lever of its own — no other row's command watches, the nine non-JavaScript ones each running once and exiting, and `make test` carrying `CI=true` unconditionally because a recipe hands its environment to whatever runner it reaches — and a build system that runs its units under one command needs the question the two divisions answer: whether one row can carry them all, or whether each unit needs its own.

## Known limits

Three limits ship with the current behaviour. Each is disclosed in the return: the agent opens a note whose harm the `Status` and the counts cannot show with the literal `CAVEAT: `, and every caller surfaces marked lines whatever the status was — including `OK`.

**A `make test` recipe driving two or more suites of the same framework reports correct counts and unattributed test names.** The wrapper rule is asked of a candidate before either division, so a candidate a `Makefile` drives is folded and never divided — which also brings the `workspaces` or `[workspace]` units of a folded candidate under this limit. `make test` runs once by construction, so a test identifier printed by more than one of them is recorded once and a loss in one is masked by another's copy: measured, the baseline recorded 3 identifiers for 4 passing tests, nothing landed in *Missing from run*, and the run returned `OK` on a real regression. The counts, the status and the per-suite marker stay correct, and a unit that goes away entirely is not masked at all. `### Notes` names every candidate the row folded and every unit of a divided one it took, says the identifiers are not attributed to them, and carries the mark.

**A `grunt` or `gulp` task that configures Karma inline, naming no `configFile`, still runs to the per-suite bound.** `grunt-karma`'s own README calls that the recommended configuration, and it leaves nothing to hand `karma start`, so there is no single-run command to rebuild the suite into. It runs the table's own `CI=true npm test`, the watcher runs to the ten-minute bound, and the row reads `RUN_FAILED` — a suite that was fine, recorded as a runner failure. It is reported rather than rescued: `### Notes` names the script and what could not be rebuilt. If a suite of yours stalls for the full ten minutes, this is the shape to look for first.

**Two or more suites of one framework that relocate between the capture and the verify call pair with nothing.** A verify pairs each suite to its baseline row on framework **and** marker value, and falls back to a move only where exactly one baseline row and exactly one detected suite of that framework are left unpaired. Where more than one of each is left, nothing can say which moved to which, so none of them pairs: the baseline rows count as gone and their tests land in *Missing from run*, which is regression-severity, while the suites found at the new paths count as new — on a tree that may have lost nothing. A divided candidate reaches this with a single move, because moving a `workspaces` or `[workspace]` root moves every one of its rows' marker paths at once. `### Notes` carries both halves. One suite that relocates on its own is unaffected: it pairs by the fallback, and the verify rewrites its prefix before comparing.
