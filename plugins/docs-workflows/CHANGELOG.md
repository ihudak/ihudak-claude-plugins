## [1.2.2] — Unreleased

**Update `workflows-core` to 1.7.1 with this plugin.** Each change below that rests on it carries its own **Rests on `workflows-core` 1.7.1** clause, naming the part of 1.7.1 it rests on; an entry without that clause rests on no `workflows-core` change.

### Fixed — `/document` and `/release-notes` stopped on an Epic address before its branch, and tested a `focus_key` they never set

Both commands take an `EPIC-` address — `/release-notes` stops without one on *"needs a PRD or Epic address"*, and both name `/product-workflows:epics` as what creates an `EPIC-` folder in their `absent` stops — and both scoped their change-scoped phases to the Epic *"when `focus_key` is set (the address resolved to an Epic folder)"*. No step set `focus_key`, and Phase 3 of each read *"the resolved folder"* for `prd.md` and stopped where it *"holds no PRD"*: on an Epic address that is the Epic folder, which holds none, so the run stopped on the re-enter/cancel escalation before the branch it was meant to take. Phase 0 step 1 of each now places the resolved folder as `workflows-core:addressing` §4.1 does and carries `<PRD>` — the PRD folder's key, the resolved folder's own at PRD level and its parent's at Epic level — and `focus_key`, the Epic's key at Epic level and `null` at PRD level. Phase 3 reads the PRD folder for `prd.md` and for its no-PRD stop, and every later *resolved PRD folder* means that folder: `/release-notes` reads `change_type` and `release_notes_category` off its `prd.md`, resolves `<PRD>` for the PRD's specs dir its `run_phase` globs, and titles a new `release-notes.md` with the PRD folder's key, as `release-note-types.md` §1 now names the title. `/document`'s change-scoped phases now include Phase 4, so an Epic-level run resolves only the repositories the focus Epic's record names: reading every record under the PRD, as Phase 3 does, it would otherwise have put every other Epic's repositories to the mount gate and handed Phase 5 a repository with no focus ref, which `diff-summarizer` refuses. A BRD container, whose PRDs sit in its slices, and a folder §4.1 places at no level stop in Phase 0 on the same escalation, a container's slices named as addresses to re-enter, where a container used to reach that stop only in Phase 3, after the plan. `doc-planner`, `doc-reviewer` and `release-notes-writer` describe the folder read they are handed as the PRD folder's, and `doc-reviewer`'s review method, which read the PRD folder *"under `<prd-products/<KEY>/`"*, a path nothing in the tree has, reads under the PRD folder path it is handed. `/document`'s citation of *"§4.1"* for the tree stopping at the Epic folder, which named no section of that command, cites `workflows-core:addressing` §2, whose kind order ends at `EPIC`. The two command pages say what an Epic address does. **Rests on `workflows-core` 1.7.1**, whose `addressing.md` §4.1 is the placement both commands now follow and whose §4 is the carrier `<PRD>` is read off. **Population: every keyed `/document` or `/release-notes` run given an Epic address, and every one given a BRD container.**

### Fixed — a PRD-level run read the PRD folder's `implementation.md` alone, while a run that implements an Epic records its work in that Epic's folder

`/dev-workflows:implement` records a run addressed to an Epic in that Epic's folder — and, from `dev-workflows` 4.1.2, a run that chose the Epic under a PRD address too, through its picker or as the PRD's only Epic, which until then it recorded in the PRD folder. `/document` Phase 3 read the PRD folder *"full depth"* and said to read *"every block under the PRD"*, while its step read `implementation.md` *"in the resolved folder"* — one file, the PRD folder's — and `/release-notes` read that one file too; so a PRD-level run's diff sources left out every Epic-addressed implementation, which reached the run, if at all, through the commit scan as unrecorded work. On a PRD-level run both now read the PRD folder's `implementation.md` and every `EPIC-` folder's under it, and on an Epic-level run `/release-notes` reads the focus Epic's own. Both say why — the record lives in the folder of the unit implemented — and cite `workflows-core:implementation-format` §1 for a block an earlier `/implement` left in the PRD folder for an Epic it chose there, which names no unit and so counts as the PRD folder's: a PRD-level run reads it and an Epic-level run does not. **Rests on `workflows-core` 1.7.1**, whose `implementation-format.md` §1 now says where the record lives and whose such a block is. **Population: every PRD-level keyed `/document` run, and every PRD-level `/release-notes` run with diff grounding on, over a PRD any of whose Epics `/implement` recorded in the Epic's own folder.**

### Fixed — a release note drafted for one Epic moved every other Epic's block boundary

`/release-notes` Phase 3 read *"only the blocks appended since the last section was written to `release-notes.md`"*. That file is the PRD folder's, one for the PRD and every Epic under it, so a note drafted for one Epic moved the boundary past the blocks another Epic had recorded before it, and that Epic's next note left them out; a PRD-level note drafted after an Epic's re-read the blocks the Epic's note had described. Naming the blocks a run used made a wrong boundary visible, and did not prevent it. **Population: every `/release-notes` run with diff grounding on over a PRD that already carries a note drafted at another scope — an Epic's beside the PRD's, or another Epic's — which only this release reaches, its first entry being what lets an Epic address draft a note at all.** Phase 8 now writes a scope line above each draft it appends, `<!-- release-note scope: <KEY> <YYYY-MM-DD> -->`, naming `focus_key` or `<PRD>` and the date, and `release-note-types.md` §1, which owns the file's layout, defines it: an HTML comment, rendering as nothing and no part of the draft, and a draft carrying none — every one appended before this release — counts as the PRD's, dated by the file's last write before a scope line reached it. Phase 3 takes its boundary per record from those lines: the blocks dated after the latest note covering that record, a note for the PRD covering every record and a note for an Epic that Epic's alone. The invariant that the draft carries no identifier now says the scope line above it is not part of the draft, and the command page says where the line sits and what it does. **Rests on `workflows-core` 1.7.1**, whose `implementation-format.md` §4 now states `/release-notes`' boundary per scope and a block dated the day of the note as read.

### Fixed — two citations named a numbered section `workflows-core:docs-grounding` does not have

`/release-notes`' usage line said `--docs <path>` is declared for every consumer by `workflows-core:docs-grounding` *"§1's *Flags first* rung"*, and `docs-workflow/repo-resolution.md` §0 called `${DOCS_PATH:-/workspace/docs}` the grounding root *"`workflows-core:docs-grounding` §1 resolves"*. That reference has no numbered sections: *Flags first* is step 1 of its *Procedure*, and the root is resolved by step 2, *Resolve the root*. The two now cite *Procedure* step 1 (*Flags first*) and *Procedure* step 2 (*Resolve the root*). `product-workflows` 3.7.0 corrects the same citation in seven of its commands. **No run's behaviour changed. Population: every reader following either citation.**

## [1.2.1] — 2026-09-18

### Fixed — a cancelled `/docs-init` printed a report four of whose sections had no value it could carry

Phase 2.5's **Cancel** jumps straight to the Phase 8.5 report, *"which states plainly that Phase 2.5 was cancelled"*. Four of that report's nine sections had no value such a run can print: `### Scaffold` (Phases 3, 4 and 6 never ran), `### Branding` (whose only "not applied" value asserts `--no-brand`, a flag you did not type), `### Verification` (four PASS/FAIL rows for checks that never ran, whose only N/A reason is `--public-only`) and `### PR draft` (a title and body for a branch that does not exist). So the one path the phase routes a cancel down could not be reported without inventing four facts. Each now carries a cancel value, worded as the sibling `/docs-brand` already words its own — that command covers every section its identical cancel-to-report jump reaches, which is what makes this an omission rather than a convention.

### Fixed — the hook preloads context for `/release-notes` only in its plugin-qualified form, and now says so

`hooks/preload-context.sh`'s own header said it matches its two commands *"bare or prefixed"*, contradicting a comment fifty lines below it in the same file, and `docs/reference/hooks.md` carried the same error twice. Measured across six prompts and three scripts: **`/release-notes PRODUCT-1234` emits nothing**, while `/docs-workflows:release-notes PRODUCT-1234` emits four lines of context — because Claude Code ships a built-in of that bare name and the built-in wins it, so the branch is deliberately qualified-only. (`/document` is unaffected: it matches bare or prefixed.) Both the script header and the page now state the asymmetry **with its reason beside it**, since a list of names a reader can act on wrongly needs the reason where they meet it. The shared disjointness paragraph in all three family hooks also claimed *"one regex apiece"* (this plugin and `dev-workflows` have two each; five across the three) and an *"optional plugin-name prefix"* (mandatory in two of the five); its conclusion holds and is kept, and the two stale premises are replaced by what the regexes do. Behaviour is unchanged and was re-measured over seven prompts × three hooks: no prompt emits from more than one plugin, and every script still exits 0.

### Fixed — two pages told a docs repo to point `frontmatter.default_owners` at its own owners list, which nothing resolves

Two prose sites instructed a docs repository to repoint that field. **No consumer resolves the pointer**: `hooks/changelog-owners-reminder.py`'s `_required_owners()` builds the path from `CLAUDE_PLUGIN_ROOT` unconditionally, and the `docs-frontmatter` skill hard-codes the same bundled path — and one page of this same plugin already said so outright, its hook description reading *"that path is fixed, read from this plugin's own bundle rather than from the profile's `frontmatter.default_owners` pointer, which the hook never reads"*. So the tree held a reference page calling the pointer unread beside two prose sites telling you to set it. Measured on a purpose-built docs repo whose in-repo profile sets `default_owners: .dev-workflows/my-owners.txt` (alice, bob) and whose tracked-and-modified page already carries both, the shipped hook answers `owners: add docs-owner-placeholder` — the plugin's placeholder, demanded on a page that already satisfies the repo's own declared list, on every edit in that space. **Retired rather than wired, and the population is what decides it**: the field has exactly two writers, `/docs-profile` — whose own instruction is *POINTERS ONLY — set `default_owners: references/docs-profiles/default-owners.txt`*, the bundled path — and `/docs-init`, told to write pointers to this plugin's own bundled files, so no profile this plugin writes ever points elsewhere and the only way a repo-local list arises is a human following the two sentences now retired. Wiring the field would mean changing both consumers at once — an author following either alone leaves the other demanding the placeholder — to serve a population that exists only because of the defect. Neither site instructs an action now, because there is no working route to instruct: each states which file is read and that the pointer is not resolved. The schema is deliberately untouched; it neither instructs repointing nor claims the field is read, and its worked example already carries the bundled path.

### Fixed — `release-note-types.md` classified against a term the tree had retired

Section 2's third classification rung read *"For a Value Increment this is the overwhelmingly common case"* and used the current name one clause later, so the rung classified against a term nothing in the tree still defines. It survived thirty-three review passes because the retired term straddles a hard wrap — `**For a Value` / `Increment this is…` — so a line-based `grep` over `plugins/` returned nothing; a wrap-insensitive sweep of the whole repository now puts every remaining occurrence in history.

### Fixed — the `$GIT_USER_INITIALS` page put the fallback prefix inside the ladder, ahead of a prompt the reference makes mandatory (1.0.0)

`docs/reference/environment.md` called the variable *"rung 1 of the **five-rung** ladder `workflows-core:branch-naming` §2 fixes"* and then enumerated *"`$GIT_USER_INITIALS` … → `git config user.initials` → inference from existing branch names → **the per-command fallback prefix** → a mandatory prompt if nothing above yields anything"*. The line now states both branches rather than the first. **False the day it was written:** `835726b5` (2026-09-05) authored both sentences for this plugin's new docs tree at **1.0.0**, and §2.4 and §2.5 already read as they do now at that commit. **Nothing gates either sentence** — with both restored verbatim the nine-gate CI chain exits **0**, verified by mutation.

`docs/getting-started.md`'s "Your first run" walkthrough told a first-time user the keyed run *"resolves the pull requests named there to local clones"*, on the same page as the `### REPOS_PATH` section this release had already corrected to name the repositories the implementation record and the commit scan name; and `README.md` still called the agent pool's second job *"PR-diff summarising"*. ### Fixed — `/document` and `/release-notes` dispatched without a model tier, against the plugin's own universal (1.1.3)

`docs/reference/agents.md` states that the six agents carrying no frontmatter pin "are assigned a tier by the dispatching command", and `/document`'s keyed mode says the same twice of itself — as a role→chain map at Phase 1.5 and as an ALWAYS invariant that names `doc-fixer` among the mechanical steps. Three keyed `doc-fixer` dispatches contradicted it outright: Phase 6.5's build-content-failure branch, Phase 7's BLOCK branch, and Phase 7's "Manual fix notes" resolution. Direct mode was bare throughout — the Phase 2A exploration subagent, Phase 3.5's `docs-style-checker` and the `doc-fixer` behind it, and Phase 4's four maintenance agents — and `/release-notes` Phase 7 dispatched `prose-style-checker` and `prose-fixer` the same way. Each now pins the Sonnet detection chain its role is mapped to; direct mode names that chain literally, because it resolves no `model_routing` block, and its "NEVER invoke Opus" invariant is what the pin honours rather than contradicts. `docs-style-checker` dispatches `prose-style-checker` itself, with no command in the loop, and now pins it too. Direct mode's maintenance apply mechanism also says *"same general-purpose agent **and model** as Phase 4"*, which is what keyed mode already said of its own.

`pr_refs` was an input nothing in the tree could build. `/document` Phase 5 passes `repo_path`, `repo_url_slug`, `refs`, `context`, `keys_hierarchy` and `refresh`; `/release-notes` Phase 5 passes the first three. Neither builds a `pr_refs` element, and neither can: producing one means resolving a pull-request URL, which both commands' own zero-API-calls invariant forbids. Everything gated on it was therefore unreachable machinery — the host-routing table, the `gh` GitHub resolver, Strategies 1–3 (all keyed on `pr_id`), the URL parse notes, the `status: MERGED | OPEN | DECLINED | UNKNOWN` field, the note on non-MERGED PRs, and the `host: other` unsupported-host disposition — sitting two lines below the agent's own sentence that *"nothing in this plugin reads a tracker or a pull-request API any more."* Retired from `agents/diff-summarizer.md` and `references/handoff/diff-summarizer.md` together, so the two state one contract, and the agent's user-visible `description` — *"Host-aware resolver — uses the gh CLI for GitHub when available"* — now says what it does.

What survives is what a `refs` element reaches: the direct `git diff <branch_to>...<branch_from>`, and Strategy 4, renamed **Key-commit fallback**, which is keyed on `keys_hierarchy` — an input `/document` does pass — and is the only way a squash-merged ref, whose branch is gone and whose sha was rewritten, is recovered at all. Also retired, as reachable only through `pr_refs`: `per_pr.pr_id` / `per_pr.url` and their `unresolved_prs` twins, which could only ever be null; the `resolved_via` values naming a retired strategy; and `unresolved_prs.candidates`, whose one documented producer was Strategy 4's single-key sub-branch keyed on `source_item`, a tracker field that appears nowhere under `plugins/`. `/document`'s all-unresolved gate loses its *"Review candidates one by one"* option with it — an option that could only ever present an empty list. `NO_PRS_RESOLVED`, `per_pr` and `unresolved_prs` keep their names: both callers match on the first, and renaming an identifier across callers buys nothing here.

### Fixed — `/release-notes` and six reader-facing surfaces described a run that resolves pull-request URLs (1.1.3)

`release-notes.md`'s invariant read *"ZERO external API calls — PR URLs are identifiers only; all resolution is local `git`"*, describing an input that command has never had: Phase 3 builds its refs from `implementation.md` and a `git log --grep` scan, and Phase 5 passes `refs[]`. Its Phase 1 sentence about *"the `pr_refs` elements that have a `status` field"* named a shape that no longer exists. Five documentation pages carried the same vocabulary — `docs/workflow.md` had keyed `/document` *"resolve PR URLs to local clones"*, `docs/getting-started.md` had it resolve *"each pull-request URL"* under `$REPOS_PATH`, `docs/reference/agents.md` described the agent as *"host-aware"*, `docs/reference/environment.md` had `$REPOS_PATH` *"read fresh by each run that resolves PR diffs"*, and `docs/commands/release-notes.md` explained what happens to *"a PR URL that appears anywhere in the inputs"*. Each now states what the run resolves: the repositories its implementation record and commit scan name, matched by `git remote get-url origin` slug. The sixth is the worst in kind and sits outside every plugin, in the marketplace's own `README.md` Prerequisites: it told the user `gh` + `gh auth login` *"enables reading GitHub PR diffs (`/document`, `/release-notes`); without it those commands fall back to local-git strategies"* — an install-and-authenticate instruction sold on a promise that was empty, since local git is the only path either command has ever taken. It now names what `gh` actually buys: the pull request `/document` offers to create, and the one every phase handoff opens in the specs repo.

### Fixed — `/document`'s `### Refs in scope` block could print an unresolved element twice (1.1.3)

`diff-summarizer` declares `per_pr` as one entry per **input** element, with `unresolved` among its `resolved_via` values, and `unresolved_prs` as the unresolved elements with their reasons — so an element that resolved to nothing is in both lists, and a report block reading *"one line per `per_pr` element … then one per `unresolved_prs` element"* prints it once from each. Settled from the command's side, which is the side that renders: the first shape is now *one line per **resolved** `per_pr` element*, and the block says an element that resolved to nothing is printed once, from the second list. The agent's contract is unchanged. The template line beneath that lead-in kept offering `unresolved` in its `resolved_via` slot — the value the lead-in had just excluded — which half-reinstated the double print for a run following the template literally; the enum is now `[local_ref | key_commits]`, and `unresolved` remains a legal value of the agent's output, just never of a line in this list.

### Fixed — three agents attributed claims to PR URLs the summaries never carry (1.1.3)

`doc-planner` step 2 told the planner to record *"which `diff-summarizer` PR URLs back it up"*, its checklist schema typed `sources: [<key | PR URL>, ...]`, and its NEVER rule required every source to be *"a key in the `folder_read` or a PR URL in `diff_summaries`"* — a traceability requirement no run could satisfy, since a `diff_summaries` entry is identified by its `ref`. `doc-writer` step 6 sent *"per-claim attribution to resolved keys and PR URLs"* into its return payload, for the same absent field. `doc-reviewer`'s Factual-correctness dimension checked claims against *"the PR diff summaries"* by the same wrong name. ### Fixed — `/document`'s Final Report asked for three things the run cannot produce (1.1.3)

Phase 9's `### PRs in scope` block instructed the run to print, per element, a **PR URL**, a `status` of `MERGED | OPEN | DECLINED | UNKNOWN`, and a `resolved_via` drawn from a six-value list. None of the three survives contact with what the run holds. `diff-summarizer`'s Output declares no per-element `status` at all — its `status` is per repo — so the field had no source; a keyed run builds `refs[]` from `implementation.md` and the commit scan, for which that agent sets `url: null`; and the `resolved_via` list omitted `local_ref`, the one value a `refs` element can ever carry. The same file's Phase 4 step 1 already stated flatly that *"there is no `pull_requests[]` to filter and no PR `status` to filter on"* — two live contradictory instructions in one command body, which `workflows-core:instruction-file-maintenance` names as a defect in itself. The block is now `### Refs in scope`, its fields taken from that agent's Output and nothing else: `ref` (or `url` on an element carrying one), the full seven-value `resolved_via`, the change counts, and a second line shape for an `unresolved_prs` entry with its reason.

### Fixed — the rest of `/document`'s pull-request vocabulary (1.1.3)

The command resolves no pull request: it resolves the implementation record's **repo slugs** to clones and summarises the **refs** that record names. Thirteen sites still said otherwise and are corrected against what the run does — the frontmatter `description` and the opening summary (*"resolves PR URLs to local git repos"*), the refresh choice and its rationale, the `diff-summarizer` dispatch prompt (*"Summarise this repo's PRs"*), the `NO_PRS_RESOLVED` handling and the all-unresolved aggregate gate, the maintenance key-events line, the `### Repos analysed` counts, the traceability rule, and the two direct-mode boundary sentences. `NO_PRS_RESOLVED` keeps its name — it is the agent's own declared return status — and every remaining "PR" in the file is the run's **own** pull request (the Phase 8.5 draft, the profile PR, a repo's pre-PR checklist), which is correct. `workflows-core:escalation-rules`' *Repo unresolved (zero matches) — /document* array offered *"Skip and continue without its PRs"* and now names refs; four sentences on the command's own documentation page follow, including its zero-direct-API-calls paragraph, which described a `gh` resolution path a keyed run cannot reach.

### Added — the cold-start scaffold: `/docs-init`, `/docs-brand`, `/docs-serve`

Three commands answer the question the plugin previously could not: *there are no docs and no docs repo — what should exist?* Every existing command assumed documentation already existed, and documented a delta against it.

- **`/docs-init`** scaffolds a documentation repository from nothing: a product-shaped Material for MkDocs page skeleton with a stub in every section, **two builds over one content root** (public and internal), a nav generated from frontmatter `order`, Vale with a project vocabulary seeded with the product name and the scaffold's own stub vocabulary, a CI workflow that runs both builds and the two output-level visibility gates, a `.gitignore` for the build outputs, the synced Vale packages and `/docs-serve`'s state file — **created, or merged into**: an existing `.gitignore`, such as a hosting template's, gains only the lines it lacks and never loses, reorders or rewrites one of its own, and, immediately before the commit, every path the run wrote — the branding phase's logo and stylesheet included — is tested against it: a path a project line ignores is left uncommitted, never force-added, every config reference to it is removed so the committed `mkdocs.yml` names no missing file, and both are reported — and the `.dev-workflows/docs-profile.yml` that `/document`, `/docs-brand` and `/docs-serve` read (`/release-notes` reads none). It branches before it writes, verifies the scaffold builds and lints, and finishes on a **drafted** pull request it never pushes. Its lint applies **the same Vale exit criterion its CI workflow applies, over the same configuration** — it runs Vale on the repository's configuration alone, with the machine's global configuration and any `VALE_CONFIG_PATH` set aside, which is what CI's bare `vale docs/` reads on a GitHub-hosted runner, and its `vale sync` runs the same way, so the packages it installs into the repository's `styles/` are the ones the repository's `.vale.ini` names — so a local pass on the scaffold's files is the verdict CI's first run reaches on them, and the stubs pass: they raise no error-level alert against the seeded vocabulary. What can still make the two differ `scaffold-tree.md` §7 names: a scaffold path a project `.gitignore` line keeps out of the commit, a newer Vale release or synced package on the runner, and a runner of the project's own that carries a Vale configuration of its own. It validates the **effective** theme, following `INHERIT`, so the inheriting `mkdocs.internal.yml` the scaffold writes is accepted rather than refused, and it writes `theme` and `extra_css` only into the config that inherits nothing — never a second theme block into the inheriting one — and the `logo`/`favicon` keys only when it applies a logo. - **`/docs-serve`** starts, stops or checks the docs site's dev server for any profiled repo and reports a URL that actually opens from the host. It never starts a second server on a port that already answers, falls forward to the next free port on a collision and says so, and `--build` runs the profile's build command and exits. **A port counts as free only where nothing answers on it and nothing is listening on it** — a listener bound to an address `localhost` does not reach answers nothing — read as `render-verification.md` §2 defines free, for the render check's pre-boot probe too; whether any other socket standing on a port refuses a bind is in no table, so a start that exits before its port answers is read as a collision wherever something is listening on that port, or its log names an address-in-use failure — both asked, since a connection's local end standing on the port is no listener and each tool words that failure its own way, some of them naming no port (`EADDRINUSE`, *Address already in use*, *Port &lt;n&gt; is already in use*). **The port reaches a server only through the `{port}` token in its recorded command**, which every run replaces with the port it serves on — the configured one, `--port <n>`, or the one a collision moved it to — and which is the only part of a command ever rewritten; the same substitution identifies a moved server by its command line. A command without the token is **fixed-port**: it binds its own port, so a collision on it is reported with what holds the port (`DOCS_SERVE_PORT_HELD`) instead of falling forward, `--port` on it stops (`DOCS_SERVE_FIXED_PORT`), and no pre-scan looks above its port for a copy nothing could have moved there. Before it starts a server it checks the command's tool, as `toolchain-preflight.md` §2 defines one. For `pnpm`, `npm` or `yarn` it also checks the dependencies installed beside the lockfile: `node_modules/`, or the `.pnp.cjs` a Yarn Plug'n'Play install keeps instead. Where either is missing it stops with `DOCS_SERVE_NO_SERVER_TOOL`, rather than wait out the readiness timeout for a server that could never start. It starts a server in a process group of its own, as `/document`'s render check boots one, and a command that exits before its port answers — `mkdocs` with a theme that is not installed, a script its package does not have — ends the readiness wait as soon as that group is gone: the exit is reported with the last lines of the command's log, and nothing is recorded, rather than the timeout being waited out and the server recorded as one that might still come up. Its pid record is **keyed by port**, because a port holds one server and the profile `/docs-init` writes serves one space twice (public and internal), and each entry names the server it started — its space, and its **visibility** where the profile tags one. A lookup made through the server selection — every serve run's already-running check, and `--status`/`--stop` with `--internal` — **filters on the recorded server before matching a port**, so a server a collision moved onto another server's configured port is never reported as that one: a public server on the internal server's port is never taken for the internal one, `--stop --internal` never stops it, and one space's server is never taken for the next space's. With no record to consult, **a server is identified by evidence, never by the port it answers on**: the process the socket table names for the port — first its checkout, the git top level of its working directory compared as a whole path, so the checkout test never takes a `git worktree` nested inside the main checkout for it (outside any git work tree, where no worktree can nest, the docs directory or any directory below it, each path read as `builtin cd "<dir>" >/dev/null && builtin pwd -P` prints it, so a `cd` or a `pwd` of the user's cannot print into it), then the command line it or a process it descends from was started with — or, for a process in this checkout whose command line names no server, where the profile's builds carry different site names, the home page's whole site name, which never overrides a server the command line names. **The process is asked before the page**: a process in this checkout started with one of the profile's commands is that server whether or not its page names the site, so a client-rendered site whose page names nothing — a VitePress dev server's shell carries an empty `<title>` — is re-adopted rather than walked past and started a second time, and whether a page names the site decides anything only where the evidence names no server; anywhere else it only helps name what holds the port. A command started through `npx` is matched by the `npm exec` command line `npx` rewrites itself to. A recorded command carrying quotes is matched too: the comparison removes every `'` and `"` from both sides and collapses each run of whitespace, since the shell strips the quotes before the server sees its arguments and the Bash tool's wrapper writes each `'` as `'"'"'`. Where one command line carries several recorded commands and they nest (`pnpm start` inside `pnpm start:internal`), the longest names the server, since a process started with a shorter one never carries the longer one's text; two unrelated commands on one command line name none. A recorded command that begins `cd <dir> &&` or with a `VAR=value` assignment is matched by what follows them, as `toolchain-preflight.md` §2 finds a command's tool: the shell consumes both, so a server's own command line carries neither, whether it was typed by hand or started by this command. **It reads which process holds a port, and that process's working directory, parents and command line, from the socket and process tables, and never guesses without them.** On Linux it reads the kernel's own tables under `/proc`: `/proc/net/tcp` and `tcp6`, and each process's `fd` links, `stat`, `cmdline` and `cwd`. They need nothing installed and no root for the user's own processes, so it runs as it is in a slim container that ships neither `lsof` nor `ss` and drops root before anything could be installed. Elsewhere it reads them with `lsof` and `ps`, which macOS ships. `render-verification.md` §2 defines each read once, and `/document`'s render check reads the tables the same way. Each read runs its utilities as `command <name>`, and the socket read's `ls` as `QUOTING_STYLE=literal command ls`, since the Bash tool's shell carries the user's aliases and exported environment: an `ls` alias carrying `-F`, `--color=always`, `-Q` or `-L`, or an exported `QUOTING_STYLE` that quotes, would leave the read naming no process for a port `lsof` and `ss` name a listener on. It stops before it probes, starts, stops or records anything where `curl` or `bash` is missing, or, off Linux, `lsof` or `ps` (`DOCS_SERVE_NO_PROBE`, `DOCS_SERVE_NO_BASH`, `DOCS_SERVE_NO_SOCKET_TOOL`, `DOCS_SERVE_NO_PS`), each tested as a binary rather than by a bare `command -v`, which an alias or a shell function of its name passes, and prints every missing tool's message at once — save a missing `bash`, reported on its own, since that test runs through `bash` and would report every other tool missing with it: without a socket table nothing can say which process holds a port, so every identity given to one would be a guess. `--build` needs none of them. A port whose process the socket table does not show — one another user runs, say — names no server, whatever its page says. A server established as another checkout's — its process named by the socket table, its working directory in another checkout — is never re-adopted or recorded on that evidence, so one checkout's `--stop` never ends another's server; a member of the process group this run started is the exception, recorded whatever its checkout — a command's `cd` into a repository nested below the docs directory leaves its server standing in one — because it is this run's own server, as the membership rule below says. The selected server is re-adopted wherever it is found, on every profile — at the configured port, on the collision walk, and, before anything starts, on the ports a collision would have moved a `{port}`-carrying command to, whether the configured port has come free since or is still held, since a moved copy can sit beyond the first free port — and another of the repository's servers is passed over. Once the server it started answers, a process in the process group it started is that server, whatever its command line says, and is recorded as such: npm rewrites its own command line as it runs, dropping its options and the `--` before the script's, and two servers whose commands differ only by a leading `cd <dir> &&` leave the same command line behind, so in those cases no command line could say it. Anything else that answers there is recorded only where the already-running check would re-adopt it as the selected server, its listener this checkout's — the same server another run in this checkout started a moment earlier, whose record the port key then replaces; where another checkout starting at the same moment, another of the repository's servers or a foreign process won the port instead, it records nothing and names what holds it. Only where nothing names the server and its page names the site does a one-server profile re-adopt it by that page, and then only where the socket table places its process in this checkout; anywhere else — a multi-server profile, or a process the table does not show or cannot place — it is reported unconfirmed, starting nothing and naming the process to stop by hand or, where the command carries `{port}`, `--port <n>`, which runs no such pre-scan. The recorded pid is always the listener's, never a wrapper's, so `--stop` never ends a wrapper and leaves its server serving, and it reports a server stopped only once no process on its port is identified as one of the repository's servers and, where nothing there is identified at all, the port no longer answers as this docs site. Where the process group it signals still runs after `SIGKILL` — or, for an entry that records no group of its own, the process it signals still holds the port — `--stop` says so and keeps the entry, so a second `--stop` can signal it again. Every re-adopted server is recorded with its listener's pid; an entry is recorded without one in two cases only — a server that had not answered when the readiness wait ran out, and a started server's port whose process the socket table does not show, another user's or a container's published port. A server it started is also recorded with the id of the process group it started it in and the start time of that group's leader, and `--stop` ends it through that group, wrappers and all — a timed-out server before it binds, too, so a slow server never comes up unrecorded after `--stop`, whatever its command line carries — but only while the group's leader still leads it with that start time, since a group id is reused as a pid is, and a process that takes a reused one started later; `--status` reports such a server that has not yet bound its port as starting — whatever pid its entry recorded, the group being the evidence there as it is for a living entry, so a server caught between one listener and the next is reported as coming back rather than as stale — and a serve run counts it as running, reporting it still starting and starting no second copy, while another server's serve run counts that port as taken, at its configured port and on its collision walk, rather than start there from under it; `--status` gives its entry the listener's pid once a process in that group holds the port. Its entry also records the log its start wrote under the temporary directory, which `--stop` deletes wherever it removes the entry, stopped or stale — only ever a regular file named `dw-serve-…`, whatever the state file names — so a long-running server's log is not left to grow once its record is gone. A run leaves no log that no entry names, save one interrupted between starting a server and recording it: a run that records nothing for what it started deletes its log itself, and a write that replaces an entry takes over that entry's log where the replaced entry's process group is still its own and holds the listener the new entry names, and deletes it otherwise. An entry recorded without a pid and without such a group is judged by what now holds its port: where the already-running check would re-adopt it as the entry's own server, the entry takes the listener's pid, and `--stop` ends it like any other; where another checkout's server, another of the repository's servers or a process that is not this docs site holds the port, or nothing answers there, the entry is stale, and `--stop` removes it without signalling anything; only where nothing identifies what answers, and it answers as this docs site, does the entry stay without a pid, and `--stop` cannot end it and leaves it in place. A recorded pid counts as living only while the socket table still names it on its port, so a pid number reused after a container restart is never reported as the running server and never signalled; an entry that records a process group of its own counts as living, too, while any member of that group holds its port, whatever pid it recorded — so a server that re-spawns its listener under a new pid in the same group is still found by `--status` and by a serve run, as `--stop` already found it — and it takes that member's pid. With `--status` or `--stop`, a bare `--port <n>` names the server bound to `<n>` — the entry recorded at that port, never one a collision moved off it — so `--stop --port <n>` stops that server without a prompt. On a profile that sets `dev_servers.concurrent: false`, it starts nothing while another of the repository's servers is known to be running — a living recorded entry, one recorded and still starting, or one its own port checks identified, which on such a profile take in every other server's configured port — and stops with `DOCS_SERVE_NOT_CONCURRENT`, naming that server and how to stop it. The state file stays out of `git status`, a copy someone committed excepted, which git reports until `git rm --cached`: where no rule ignores it, the command appends that one path to the repository's local `.git/info/exclude`, never committed, so a clean-tree gate in the family does not meet it as an untracked file, in a repository `/docs-init` scaffolded or any other. `--internal` on a profile that tags a public server but no internal one — a `/docs-init --public-only` scaffold — stops with `DOCS_SERVE_NO_INTERNAL_BUILD` instead of serving or building the public site — under `--build`, with a message naming the missing `builds[]` entry. ### Changed — `/document`'s render check stops each server by its process group

The smoke-check recorded "the process id" of each server it booted and killed it before booting the next, without saying which process. Started the way the Bash tool starts a command, that is a wrapper shell, and an `npm` or `pnpm` script adds another: signalling either leaves the server serving, so the next server booted beside it. A server that had not bound its port when the readiness poll timed out was worse: killing its wrapper left it running, and it bound after the check had moved on, outliving the run. It now boots each server **in a process group of its own** — `command bash -c 'set -m; (cd <docs_repo_path> && <command>) > <log> 2>&1 & echo $!'`, where job control makes the printed pid the id of a group the command's wrappers and children inherit — and stops it by **signalling that group**, under the same explicit `command bash -c`, so job control, `$!` and `kill -- -<pgid>` are bash's whatever shell the Bash tool uses — Claude Code runs it in bash or in zsh, zsh on a default macOS — and a `bash` function of the user's never answers for the group, `SIGTERM` and then `SIGKILL`, after its pages and after a readiness timeout alike. **The next server boots only once two things are confirmed**: the group is gone, and the port is quiet. A group counts as gone where **the process table** names no member of it or where every member it names is a zombie: a zombie runs nothing and holds no port, and under a parent that never reaps — a container whose PID 1 is `sleep infinity`, with no init — a signal test alone would find the group running for good and end the check after its first server. `kill -0` settles only the other half — exit 0, so a member is alive and signallable, so the group is not gone — because its failure has two causes that mean opposite things: no such group, and a group this user may signal no member of, which `kill(2)` refuses with `EPERM` and bash reports with the same exit 1. Reading that failure as a gone group reports a live server as ended: measured against four live root-owned groups on this host, where `kill -0` exits 1 while the table names a live, non-zombie member of each. The table names another user's processes too, on Linux from `/proc` and elsewhere from `ps`, so it answers where the signal cannot. Where the port still answers, the port's **listener** is signalled as a second stop — `/docs-serve`'s definition of one, without its checkout test (this run started the server) or its state-file test (this command keeps none). Where either still cannot be confirmed, no further server boots, the record names the port or process group left running, its command and its log, and every page not yet checked falls to the manual table; a server confirmed stopped has its log removed, so the check leaves behind no log but one its record names. A server job control gave no group of its own is stopped by its pid and its listener instead, and a readiness timeout on it ends the check, since nothing can tell whether it will bind late. Every read of the process or socket table (the group a boot made, its members' states, a listener and its parents) comes from `/proc` on Linux, which needs nothing installed, and from `ps` and `lsof` elsewhere (`render-verification.md` §2), each utility run as `command <name>` so an alias or shell function the Bash tool's shell carries cannot change what the read parses. A missing `lsof` alone never ends the check. A probe before each boot keeps the check from booting onto a port something else already holds, and that process is never signalled. **The readiness poll ends as soon as that group is gone**: at every interval at which its request gets no response it tests the group, and a server whose command exits before its port answers — a theme that is not installed, a configuration it cannot load, a script its package lacks — is reported with the last lines of its log, its pages fall to the manual table, and the check goes on at once, where 1.1.3's poll ran until HTTP 200 or the whole readiness timeout, 120 seconds by default, for a server that had already exited.

It used to say "no complementary pass ran; the primary carried the gate", which mapped to `RAN`. It now says "`prose-style-checker` *was* the primary", which maps to `DEGRADED`. Same token, opposite ledger consequence, in the field `/document` derives the outcome from. Nothing else consumes it.

Everything else is behaviour-preserving.
