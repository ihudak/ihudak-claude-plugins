## Goal

Turn a refined `idea.md` + a user-supplied `JIRA-KEY` into a high-quality **Value Increment** document — the PM's crown-jewel artifact — authored to feed the existing downstream pipeline (`jira-reader` → `/specify` / `/epics` / `/document` / `/release-notes`) and published to Jira.

## Why (scope framing)

`/idea` (v2.15.0) produces the seed; `/create-vi` produces the VI. The VI is **product-level** (PRD): what/why/for-whom, not how. Code-feasibility grounding is deliberately downstream — light in `/specify`, deep in the future `/create-ard` (PA) and `/design` (dev). The VI is authored in the specs repo, published to Jira by paste + re-import.

## Research basis

Reuses this session's six-repo sweep (2026-07-10): Mike's `observability-requirements` (heavyweight VI + phase gates), Alex's `mgd-specifications` (leaner Jira VI + EARS spec + grounded ARD), BMAD (spine + adapt-in, stable IDs, reviewer gate, "substance over theater"), SpecKit (clarify/analyze), mattpocock `grilling`, and the dev-workflows downstream consumer contract (crisp goal + partitionable themes + `relevant_for_release_notes`/`release_versions` frontmatter). Not re-run.

## Decisions (locked in brainstorming)

1. **VI shape** — one `references/vi-format.md` (a mandatory **spine** + an **adapt-in menu**), authored **inline** by the orchestrator grill (like `/specify`), gated by one Opus **`vi-reviewer`**. A `--lean | --hybrid (default) | --full` flag selects the profile. **Not** three subagents.
2. **Sections** — spine below; the adapt-in menu is the **union of Mike's + Alex's** valuable sections; each cluster is **pulled only when the idea warrants it** (BMAD discipline).
3. **Home & Jira** — author `$SPECS_PATH/specifications/<KEY>-<slug>/<KEY>_ValueIncrement.md`; relocate `idea.md` there (copy/move, **never symlink**); branch+PR to specs `main` (commit-when-asked); document paste-into-Jira + re-import with `https://github.com/ivan-gudak/jira-workitem-import` round-trip.
4. **Grounding** — product-level; **no code scan, no repos required**; optional grounding in `idea.md`'s cited sources + strategy/vision docs the user points to.
5. **Grill** — relentless, via a NEW `references/grilling-technique.md` SSOT that `/create-vi` cites and **`/idea`, `/specify`, `/design` are retrofitted to cite** (removing their duplicated inline lines).
6. **Inputs** — `JIRA-KEY` mandatory (format regex only; graceful fail; auto-creates the VI dir); `idea.md` resolved via a ladder; default `--hybrid`.
7. **No HTML render** — the VI goes to Jira, which renders it.
8. **Verified (no follow-up):** `/specify` already (a) lightly grounds the spec against code (Phase 3 soft gate + Phase 4 `code-scanner`) and (b) authors Test Cases `[TCxx]` (Phase 5 stage 5, gated by `spec-reviewer`). So the VI correctly omits code-grounding and detailed TCs.

## Artifact — the VI document

### Frontmatter (PM-authorable subset; the pure Jira-mirror fields are regenerated by the importer on round-trip)

```yaml
---
title: <human-readable VI title>
summary: <one-line>
issue_type: ValueIncrement
status: <draft | …>
owning_program: <program>
tracking_programs: [ … ]
priority: <e.g. Major>
labels: [ … ]
relevant_for_release_notes: <yes | no>
release_versions: "<e.g. Managed (344), SaaS (344)>"
sources:                       # PROPAGATED from idea.md's recorded provenance — NOT the literal idea.md
  - provenance: rfe | community-post | prompt | markdown
    ref: <RFE key | post URL | …>
derived_from: <path to the idea.md this VI was built from>   # traceability
jira_key: <KEY>
---
```

### Spine (always, every profile)

`## Problem` (who hurts, why now; solution-free) · `## Goal` (crisp 2–3 sentences → feeds `jira-reader`'s goal) · `## Target audience` (personas; specific roles) · `## User Stories` (`### [US-N]` — *As a [role], I want [capability], so that [benefit]*) · `## Acceptance Criteria` (`[AC-N]` per story — externally-observable pass/fail) · `## Scope` (In / Out; both concrete) · `## Success Metrics` (`[SM-N]` — measurable, technology-agnostic).

### Adapt-in menu (profile = candidate set; each pulled only when warranted)

| Cluster | lean | hybrid | full |
|---|:-:|:-:|:-:|
| Use cases & user journey (UC-N) | – | ✓ | ✓ |
| Non-functional requirements | – | ✓ | ✓ |
| Assumptions & open questions | – | ✓ light | ✓ Contradictions-Log table |
| Why now / differentiation | – | ✓ | ✓ |
| References / linked issues | – | ✓ | ✓ |
| Documentation impact | – | ✓ | ✓ |
| Blogline (Internal+External) · Customer Zero · Competitive Snapshot | – | – | ✓ |
| Functional Requirements (FR-N) · E2E Demo | – | – | ✓ |
| UX prototype / UI mockups · API specification | – | – | ✓ |
| Key Deliverable & Plan · Enablement · Cost Analysis | – | – | ✓ |

Format SSOT: `references/vi-format.md` (spine + menu + profiles + per-section rules + frontmatter). Quality rules carried from Mike: FR/UC must not restate US; **no implementation detail** in the VI; acceptance criteria externally observable; consolidate shared data dependencies; no em-dashes-as-syntax where the repo forbids.

## Architecture — command flow (`commands/create-vi.md`)

```
/create-vi <JIRA-KEY> [@idea.md] [--lean|--hybrid|--full]

Phase 0  Resolve inputs (KEY, idea.md ladder, $SPECS_PATH, feature folder, profile; detect prior VI)
Phase 1  Configure (confirm folder/profile/idea; relocate idea.md; warn-and-fold on idea status:draft)
Phase 1.5 Classify + model routing (model-routing skill; Opus orchestrator, degrade+record)
Phase 2  Read idea.md (directly) + optional strategy-doc grounding
Phase 3  Author via relentless grill (references/grilling-technique.md), profile-selected sections
Phase 4  Opus vi-reviewer gate (profile-aware; one fix cycle + re-review)
Phase 5  Handoff (write VI dir; offer branch+PR; document Jira paste + re-import round-trip)
Phase 6  Next-step offer — BOTH /release-notes (PM now) AND /create-ard (PA handoff)
Phase 7  Terminal tail: impl-maintenance + emit-auto + emit-cost(pm/vi-creation) + capture-at-block
```

### Phase 0 — resolve inputs

- **`JIRA-KEY` (mandatory):** validate `^[A-Z][A-Z0-9_]*-\d+$`. If absent/invalid → **graceful fail**: *"`/create-vi` needs a Jira key — create an empty Jira workitem first to get the ID, then re-run `/create-vi <KEY> @<idea.md>`."* (Format only — zero Jira API, so existence is not checked.)
- **`idea.md` resolution ladder:** (1) explicit `@path`; (2) **same-session** — if `/idea` just ran, use its recorded path (confirm); (3) **discover** `$VAULT_PATH/Projects/**/idea.md` → picker; (4) prompt for a path, or — last resort — proceed and grill the VI from scratch.
- **`$SPECS_PATH` (required):** if unset, stop naming `SPECS_PATH` (`choices: ["Set SPECS_PATH (enter the path)", "Cancel"]`).
- **Feature folder:** `specifications/<KEY>-<slug>/` (`<slug>` from the idea title, else derived). **Auto-created** on first write; honor an existing dir matched by key-number (tolerate `-`/`_` drift).
- **Prior VI:** if `<KEY>_ValueIncrement.md` exists → Phase 1 offers refine-vs-fresh.
- **Profile** from the flag; default `--hybrid`.

### Phase 1 — configure

Confirm feature folder, profile, and the resolved `idea.md`. **Relocate `idea.md`** into the feature folder (copy/move, **never symlink** — a cross-root symlink between `$VAULT_PATH` and `$SPECS_PATH` would break). If `idea.md` `status: draft` (open `[NEEDS CLARIFICATION]`), **warn-and-fold**: the grill resolves those items — do NOT hard-block.

### Phase 1.5 — classify + model routing

Invoke the `model-routing` skill (`skill: "dev-workflows:model-routing"`). Classification typically MODERATE (SIGNIFICANT for large/cross-cutting VIs). Grill + authoring run **inline on the Opus chain** (`current_model`, not a delegated subagent); `vi-reviewer` on the Opus chain; any detection subwork on the §2.1 Sonnet chain. If no Opus resolves → **degrade to best-available + record** (no hard block).

### Phase 2 — read the seed

Read `idea.md` **directly** (it is the plugin's own format — `idea-reader` is for arbitrary external sources, not needed here). Extract Problem / Who / value / rough scope / signals / candidate success + any open `[NEEDS CLARIFICATION]`. Optionally ground in `idea.md`'s cited sources and any strategy/vision docs the user points to. **No code scan.**

### Phase 3 — author via grill

Conduct a **relentless** interview per `${CLAUDE_PLUGIN_ROOT}/references/grilling-technique.md`, authoring `<KEY>_ValueIncrement.md` live against `references/vi-format.md`. Walk the spine in dependency order (frontmatter incl. `release_versions` + `relevant_for_release_notes` → Problem → Goal → Target audience → US-N → AC-N → Scope → SM-N), then the profile's adapt-in clusters **pulled only where the idea warrants them**. Fold in the idea's open clarifications. `sources` propagated from the idea's recorded provenance.

### Phase 4 — review gate

Dispatch `vi-reviewer` (Opus). **Profile-aware rubric:** goal crispness (BLOCKER if vague — it feeds every consumer); US well-formed (specific role, verifiable benefit); AC observable pass/fail (no "be reliable"); scope In/Out both concrete ("future work" is a finding); metrics measurable + technology-agnostic; **no implementation detail** (product-level); FR/UC (if present) don't restate US; downstream-contract frontmatter present (`relevant_for_release_notes`, `release_versions`); profile-required sections present and any present adapt-in section is substantive ("substance over theater"). Returns PASS / PASS WITH RECOMMENDATIONS / BLOCK. On BLOCK, fix inline + re-review once; if still BLOCK, escalate per `escalation-rules.md`. Cap: one fix cycle + one re-review.

### Phase 5 — handoff

Write the feature folder (`<KEY>_ValueIncrement.md` + the relocated `idea.md`). Then **offer** (commit-when-asked — never automatic):
```
choices: ["Branch + commit + push + open PR to main (Recommended)", "Just write the files — I'll handle git", "Cancel"]
```
Branch `vi/<KEY>-<slug>`; commit ONLY the feature folder (never `git add -A`); PR targets `main`. **Document the Jira round-trip:** paste the VI body into the Jira workitem `<KEY>`, then re-import (`jira-workitem-import`) to `$VAULT_PATH/jira-products/<KEY>` so the pipeline sees it.

### Phase 6 — next-step offer (both)

Present **two parallel next steps**, clearly labeling the role handoff:
- **`/release-notes <KEY>`** — the PM can draft the initial customer-facing release note now (the cost model's `pm`/`vi-creation` inferred case: no spec/design yet).
- **`/create-ard <KEY>`** — hand off to a **Product Architect** for the grounded architecture document (a different role/session; `/create-ard` is sub-project 3).

Guidance only — never auto-invokes another command.

### Phase 7 — terminal tail

`impl-maintenance` (Sonnet) → `emit-auto` feedback; `emit-cost` (`command: /create-vi`, `phase: vi-creation`, `role: pm`, `jira_key: <KEY>`); the **capture-at-block invariant** (`emit-block` before escalating a plugin-gap halt; never for env/user halts — bad `$SPECS_PATH`, missing key, cancellation). ADDITIVE — never fails the run, never writes to cwd, no user name.

## Grilling SSOT — `references/grilling-technique.md` (NEW)

The embedded interview technique, consolidated (DRY) so four commands cite one file instead of duplicating ~5 lines:
- Ask exactly ONE question at a time; wait for the answer before the next. Never batch.
- Give your recommended answer for every question (react to a proposal, not a blank prompt).
- Fact-vs-decision split: look up facts (code / vault / context) and answer them yourself; put only decisions to the user.
- Walk the design tree in dependency order — resolve a parent decision before dependents.
- Continue to shared understanding for the current section, then write it.
- **Depth is the caller's choice:** `/idea` = bounded (≤5, `--deep` relentless); `/specify`, `/design`, `/create-vi` = relentless.
- Technique adapted from mattpocock grill-me/grilling; embedded so callers have **no runtime dependency**.

**Retrofit** (replace the duplicated inline technique lines with a one-line citation, keeping each command's own depth + stage list): `commands/idea.md` (Phase 3), `commands/specify.md` (Phase 5), `commands/design.md` (grill phase).
