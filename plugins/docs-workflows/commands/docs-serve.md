**Core references.** A citation of the form `workflows-core:<name>` names a shared reference in the `workflows-core` plugin. Load it with `Skill(skill: "workflows-core:reference", args: "<name>")` — never by path: `${CLAUDE_PLUGIN_ROOT}` resolves to this plugin, which does not carry it.

Serve the documentation site for a profiled docs repo: $ARGUMENTS

`/docs-serve` runs a profiled documentation repository's own dev server and reports a URL that actually opens from the host — on any profiled repo, not only one `/docs-workflows:docs-init` scaffolded. It reads the `dev_servers` block `/docs-workflows:docs-profile` already wrote; it never picks a generator, a port, or a start command of its own. **It writes no documentation and no artefact** — no branch, no commit, no pull request, and (see Phase 0) no `specs-preflight`. **It also runs no review gate**: D17, the family rule that every artefact-writing command passes a high-tier review before it is trusted, names `/docs-serve` as its sole exemption — precisely because there is no artefact here for a reviewer to check.

**Signature:** `/docs-serve [<docs-repo-path>] [--internal] [--stop] [--status] [--build] [--port <n>]`

## Phase 0 — Resolve

Strip every recognized flag from `$ARGUMENTS` wherever it appears — `--internal`, `--stop`, `--status`, `--build`, and `--port <n>` (consumes the token immediately following it as its numeric argument) — before reading a positional token; the flags themselves are handled in **Mode dispatch**, below. What remains is the optional `<docs-repo-path>`.

Execute **`resolve-docs-repo`** from `${CLAUDE_PLUGIN_ROOT}/references/docs-workflow/repo-resolution.md` §1 — the signal-positive form, since this command needs a docs repo that already exists, never one to create. Do not restate its ladder here; the entry point owns it. Report which rung answered, per its own hard rule — a command that quietly works in an unexpected directory is expensive to unpick afterwards.

Record the resolved absolute path as `<repo>`, and its git work-tree top level as `<repo-root>` — `git -C <repo> rev-parse --show-toplevel`, or, where `<repo>` is in no git work tree, `<repo>` itself as `cd <repo> && pwd -P` prints it. `<repo-root>` is the profile's one home (`${CLAUDE_PLUGIN_ROOT}/references/docs-profiles/docs-profile-schema.md`, **Where the profile lives**): wherever a mode below reads the profile, runs a command it records or reads and writes the state file, it does so at `<repo-root>`, the state file sitting beside the profile — also where `<repo>` is a site below that top level, such as a monorepo's `docs/`.

**No `specs-preflight`.** This is deliberate, not an omission: `/docs-serve` writes nothing into `$SPECS_PATH` — it starts a process in the resolved docs repo and reports a URL — so opening a branch discipline for a run with no artefact behind it would be ceremony. Its closest sibling is `/workflows-core:statusline`, not `/docs-workflows:document`: like that command, this one runs no `specs-preflight` and no terminal `commit-artifacts`. The only state it writes anywhere is Phase 7's pid/port record, under `<repo-root>/.dev-workflows/`, beside the profile — never under `$SPECS_PATH`.

## Mode dispatch

Exactly one of `--status`, `--stop`, or `--build` drives this run; where more than one appears in `$ARGUMENTS`, the first encountered (left to right) wins, and the run says which of the others it ignored.

- `--status` → **`--status` mode**, below. Reports recorded state; starts nothing.
- `--stop` → **`--stop` mode**, below. Stops a recorded server; starts nothing.
- `--build` → **`--build` mode**, below. Runs the profile's build command; starts no server.
- None of the three → the default serve flow, **Phase 1** onward.

---

## `--status` mode

Read `<repo-root>/.dev-workflows/docs-serve.state.json` (Phase 7 writes it). Absent, or holding no entries → report `No /docs-serve state recorded for <repo>. Nothing appears to be running (a server started outside this command is invisible to --status).` and stop cleanly — an idle repo is the ordinary state, not an error.

Otherwise, for each recorded entry — one per port, the key Phase 7 writes: test whether it is living (Phase 7), and re-probe the port and URL with the same reachability check Phase 2 uses. Report, per entry: port, space (and visibility, where recorded), pid, URL, and one of *running* (living, its port answering as recorded), *stale* (not living, or living but its port no longer answering as this docs site), or *unknown* (the probe itself failed); an entry recording no pid — Phase 2 and Phase 5 say when one is written — is judged by its port alone, and says it has no pid. A selector narrows the report to the entries **Phase 7's lookup** returns for it: `--internal` is Phase 1's own server selection for `--internal`, looked up as that server — so only entries recorded for it are reported, which on the two-server profile `/docs-workflows:docs-init` writes means those that recorded `internal` — and a bare `--port <n>` is that port, matched against every entry. With neither given, every recorded entry is reported.

## `--stop` mode

Read the same state file. Select the entry to stop through **Phase 7's lookup**, always — never by space alone:

- A bare `--port <n>` argument is the port, matched against every entry — no prompt.
- An `--internal` flag is Phase 1's own selection (steps 1–3, `--port` override included) for `--internal` — the same selection a serve run makes, looked up as that server and at its port. The lookup takes only the entries recorded for the selected server — on a profile that tags its servers, the ones that recorded `internal` — and among them the one bound to the port that selection resolves or moved off it by a collision. So `--stop --internal` stops the server a `--internal` serve run started, given the same `--port` where that run carried one. On the two-server profile `/docs-workflows:docs-init` writes, that is the `internal`-tagged server and never its public twin of the same space — not even a public server an earlier collision moved onto the internal server's configured port, which a lookup by port alone would have returned.
- With neither given and exactly one entry recorded, stop that one — no prompt.
- With neither given and more than one entry recorded, resolve it the same way Phase 1 step 3 resolves an ambiguous server: the state file holds one entry per running server, as many as there are ports in use, with no count fixed anywhere, so the same cap applies. Print every recorded entry as prose above the prompt — its port, its space, and its visibility where recorded — then:
  - **Three or fewer entries** — `choices: ["port <port-1> — <space-1> (Recommended)", "port <port-2> — <space-2>", "port <port-3> — <space-3>"]` (2 or 3 options, matching however many are recorded; a recorded visibility is appended to its option, e.g. `port 8001 — docs (internal)`).
  - **Four or more entries** — `choices: ["port <port-1> — <space-1> (Recommended)", "port <port-2> — <space-2>", "port <port-3> — <space-3>", "Another entry from the list above — name its port"]`.

  The typed answer is resolved against the ports just printed — never parsed out of the free text.

For the selected entry: where it is living (Phase 7), send `SIGTERM` to its pid; wait up to 5 seconds for it to exit; `SIGKILL` if it has not. **An entry that is not living is never signalled** — its process has exited, or its pid now names some other process — and goes straight to the re-probe; where its port no longer answers, report it as already stopped. **Then re-probe the port before reporting**, with Phase 2's tests: stopped means the port no longer answers as this docs site, and nothing short of that does. Where it still answers — a pid recorded by an earlier version that took a wrapper for the server, or a server something restarted — say that the port still answers although the recorded process has ended or no longer holds it, name its listener's pid where the socket table names one, and **never report the server stopped**. Remove the entry from the state file either way — its pid no longer holds the port, and leaving a stale entry behind is what breaks the next `--status`. Report what was stopped, or `Nothing recorded to stop for <repo>` when the file holds no matching entry. **An entry recording no pid** — Phase 2 and Phase 5 say when one is written, a readiness timeout among them — is judged by its port instead, exactly as `--status` judges it: where the port no longer answers as this docs site, the entry is stale and is removed like any other; only where it still answers is it a live server this command cannot stop, and then `--stop` says so, with its port, and leaves the entry in place.

## `--build` mode

Run the profile's build command and exit without starting a server — this is the flag `/docs-serve` carries instead of a separate `/docs-build` command: the pipeline already gates on the profile's build (`${CLAUDE_PLUGIN_ROOT}/references/docs-profiles/docs-profile-schema.md`'s field rules — an absent build command already disables `/docs-workflows:document`'s own gating build check), and a flag is cheaper than a whole command.

Resolve the command to run, most specific first:

1. The profile's `builds[]` list (the two-build MkDocs shape `/docs-init` scaffolds): `--internal` selects the entry whose `id` (or `visibility`) is `internal`; its absence selects `public`. Where the list records the other one but not the one asked for — a `--public-only` scaffold's lone `public` build under `--internal` — stop with Phase 1's `DOCS_SERVE_NO_INTERNAL_BUILD` (or `DOCS_SERVE_NO_PUBLIC_BUILD`), never building the other visibility in its place. Neither id present → fall through.
2. `commands.per_space.<space>.build`, where `<space>` is Phase 1's own selection logic, applied here even though this mode starts no server — the same space still identifies which build to run.
3. `commands.build` (flat).

No candidate resolves at any of the three → stop:

`DOCS_SERVE_NO_BUILD_COMMAND: <repo>'s profile records no build command (checked builds[], commands.per_space.<space>.build, commands.build). Run /docs-workflows:docs-profile <repo> to record one, or build by hand.`

Run the resolved command via Bash, in the foreground (this mode waits for it, unlike Phase 4's server start), from `<repo-root>` (Phase 0). Report its exit code and output; a non-zero exit is reported as a failed build, never swallowed.

## Phase 1 — Read `dev_servers` and select the server

Read `<repo-root>/.dev-workflows/docs-profile.yml` (`${CLAUDE_PLUGIN_ROOT}/references/docs-profiles/docs-profile-schema.md`). The file absent, or present but carrying no `dev_servers` block, stops the run:

`DOCS_SERVE_NO_DEV_SERVER: <repo> has no dev_servers block recorded. Run /docs-workflows:docs-profile <repo> first — it detects a repo's *:start scripts and writes this block.`

`dev_servers.servers[]` is a list, one entry per server — `space`, `command`, `port`, and optionally `base_path`, `public_base_url`, and `visibility` (`docs-profile-schema.md`'s field rules). Usually that is one per servable space, but not always: the two-build profile `/docs-init` writes records **two** servers for its **one** space, a public and an internal one, told apart by `visibility` alone — which is why the state Phase 7 records is keyed by port and never by space. A space id still labels a row of step 3's picker, beside that server's port, since the servers step 3 offers carry no `visibility` to tell them apart. Select the entry this run serves:

1. Where an entry carries the declared `visibility` field (`public | internal` — it pairs a server with the `builds[]` entry of the same visibility, and the two-build MkDocs shape `/docs-init` scaffolds records one server per build, tagged to match), `--internal` selects the `internal`-tagged entry and its absence selects the `public`-tagged one. **Where the tag asked for is on no entry, stop — never serve the other visibility in its place.** Under `--internal` with no `internal`-tagged server — the profile `/docs-init --public-only` writes records exactly one server, tagged `public` — stop: `DOCS_SERVE_NO_INTERNAL_BUILD: <repo>'s profile records no internal build — no dev_servers.servers[] entry is tagged internal. A /docs-init --public-only scaffold has none by design; adding one takes an mkdocs.internal.yml build config and a dev_servers.servers[] entry tagged visibility: internal that serves it. Drop --internal to serve the public build.` Without `--internal`, on a profile whose tagged servers are all `internal`, stop the same way: `DOCS_SERVE_NO_PUBLIC_BUILD: <repo>'s profile records no public build — no dev_servers.servers[] entry is tagged public. Pass --internal to serve the internal one.` `--status --internal` and `--stop --internal`, which make this same selection, stop the same way.
2. Where no entry carries `visibility` and the list holds exactly one entry — the ordinary case for a repo with nothing to split, including a single-space profile with no two-build scaffold behind it — use it regardless of `--internal`, and say plainly that the profile records no public/internal split for this command to honour, rather than pretending `--internal` changed anything.
3. Where the list holds more than one entry and none carries `visibility`, ask — never guess, and never render an array sized to the list: `docs-profile-schema.md` fixes no upper bound on `dev_servers.servers[]` — it states the length of neither that list nor `spaces[]`, which is "required and non-empty" and nothing more — so a naive one-row-per-server array is a tool call `AskUserQuestion` rejects the moment a profile records five servers, not a long menu. This is the same shape `workflows-core:epic-picker` *The cap* exists for — a picker built from a directory listing, with no literal options for a static check to count — so resolve it the same way. Load the reference with `Skill(skill: "workflows-core:reference", args: "epic-picker")`; cited here as the authority rather than restated.

   Print every candidate `dev_servers.servers[]` entry as prose above the prompt, one line each — its `space` id and `port` — then:

   - **Three or fewer entries** — the array carries them all: `choices: ["<space-1> — port <port-1> (Recommended)", "<space-2> — port <port-2>", "<space-3> — port <port-3>"]` (2 or 3 options, matching however many are recorded; a one-entry list never reaches this rung — it resolves at step 2).
   - **Four or more entries** — the array carries the first three plus the overflow option: `choices: ["<space-1> — port <port-1> (Recommended)", "<space-2> — port <port-2>", "<space-3> — port <port-3>", "Another server from the list above — name its space and port"]`.

   The port is on every row because nothing in `docs-profile-schema.md` stops two untagged entries sharing a space id, and two rows reading the same id would be a choice the operator cannot make. The typed answer is resolved against the `space` ids and ports just printed — never parsed out of the free text (`workflows-core:epic-picker`'s closing paragraph states the same rule for its own picker). The worked two-space profile (`cloud`, `self-hosted`) reaches the three-or-fewer case: its two servers differ by space, not by visibility, so step 1 never resolves them and step 3 prints both and asks.

**The port reaches the command only through its `{port}` token.** The selected entry's `command` may carry the literal token `{port}` (`docs-profile-schema.md`'s field rule for `dev_servers.servers[].command`), and Phase 4 replaces it with the port this run serves on — the configured `port`, `--port <n>`, or Phase 3's shift. Nothing else in a command is ever rewritten. A command without the token is **fixed-port**: it binds a port of its own wherever it starts — a baked-in `-a 0.0.0.0:8000`, or a script such as the schema's `pnpm cloud:start` that names its port inside — so nothing this command does can move it. Phase 2 runs no pre-scan for it, Phase 3 never walks it (each says why), and `--port` cannot move it either.

`--port <n>`, when given, overrides the selected entry's configured `port` for this run: Phases 2 and 3 test `<n>` rather than the profile's recorded port, Phase 2 runs no pre-scan from it, and Phase 4 substitutes it for `{port}`. **On a fixed-port command, `--port <n>` stops the serve flow here**, before anything is probed, rather than start a server that binds somewhere other than `<n>`:

`DOCS_SERVE_FIXED_PORT: <repo>'s <server> server runs "<command>", which carries no {port} token — it binds its own port, so --port <n> cannot move it, and nothing was started. Drop --port to serve it on its configured port <port>, or add {port} to the command where its tool takes a port argument (docs-profile-schema.md, dev_servers.servers[].command).`

`<server>` is the selected entry's space, followed by its visibility in parentheses where the profile tags one — `docs (internal)`. `--status` and `--stop` read `--port` as a port to look up and start nothing, so this stop is the serve flow's alone.

## Phase 2 — Already-running detection

Before starting anything, test whether the selected server is already up. **A server's identity comes from evidence, never from the port it answers on.** Every port this command judges — the configured port here, each port step 2's pre-scan probes, and each port Phase 3 walks — is judged the same way, in this order:

- **Does it answer?** The reachability probe. A port that does not answer has nothing listening on it.
- **Is a living recorded entry of another server bound to it?** One the state file records at that port for a server other than the selected one — an entry step 1 of Phase 7's lookup would not keep for the selection — that is living (Phase 7). That makes it another of this repo's servers, whatever its page says — typically one an earlier run's Phase 3 moved onto the selected server's configured port: the public twin of an internal server, or another space's server.
- **Does it answer as this docs site?** Fetch the response and test it for something that actually names this docs site (the profile's `repo.name`, or the generator's own `site_name`, whichever the repo exposes). An answer carrying no such marker is not this docs site. A marker establishes the *site* and nothing more: every server of a multi-server profile renders a page naming it, and so does the same server run from another checkout of this repo.
- **Which server is it?** Decided by the evidence below, and by nothing else.

**The evidence.** Two kinds count, and each names at most one of `dev_servers.servers[]`:

1. **The listening process.** The *listener* on a port is the process the socket table names for it: `lsof -t -iTCP:<port> -sTCP:LISTEN`, or where `lsof` is absent, the `pid=` value in the `users:` field of `ss -ltnp 'sport = :<port>'`. Where it names several processes, the listener is the one the others descend from (walk each one's parents with `ps -o ppid= -p <pid>`); where none is, or neither tool is present, or the one present names nothing, **no listener is named**.
   - **Checkout first.** A named listener's checkout is the git top level of its working directory — `git -C /proc/<pid>/cwd rev-parse --show-toplevel` on Linux, or on macOS the same command run on the path in the `n` line of `lsof -a -p <pid> -d cwd -Fn` — and this run's checkout is `git -C <repo-root> rev-parse --show-toplevel`: the top level Phase 0 recorded, computed by the same command as the listener's so the two compare like with like — never the resolved `<repo>` itself, since a docs repo resolved at a subdirectory of a work tree (a monorepo's `docs/`) runs its servers inside that same top level. Git resolves symlinks in both paths; where a directory is in no git work tree, its top level is the directory itself, as `cd <dir> && pwd -P` prints it. **Compare the two as whole paths, never as a prefix**: a `git worktree` can sit inside another checkout's tree — nesting them under `.worktrees/` in the main checkout is a common layout — and a prefix test calls that worktree's server the main checkout's. Equal paths establish the listener as **this checkout's**; different ones establish it as **another checkout's**, whether a sibling worktree, another clone or another project; where no listener is named, or its working directory cannot be read, the checkout is **not established**.
   - **Then which server** — only for a listener established as this checkout's. Walk from the listener up through the processes it descends from, up to pid 1, reading each one's command line with `ps -o args= -p <pid>` and its parent with `ps -o ppid= -p <pid>`: a wrapper — `pnpm …:start`, an npm script, the `sh -c` or `bash -c` the Bash tool itself starts — puts the listener in a child and the recorded command on a parent. The first command line on that walk carrying any server's recorded `dev_servers.servers[].command` verbatim — with its `{port}` replaced by the port being judged, since that is the command line a server serving that port was started with; a fixed-port command is compared as recorded — names that server. Where it carries two servers' commands — one recorded command can be a substring of another — it names none, and the walk stops there: **never pick the longer one**. A walk that reaches pid 1 without a match names none.
2. **The page's site name** — only on a profile where it tells the servers apart: more than one server, each pairing by `visibility` with a `builds[]` entry whose `config` is an MkDocs config that sets a `site_name` (its own key, or the one its `INHERIT` parent sets), and no two of those names the same. The two-build profile `/docs-workflows:docs-init` writes is one: `<product>` and `<product> (internal)` (`${CLAUDE_PLUGIN_ROOT}/references/docs-workflow/scaffold-tree.md` §5 and §6). Fetch the port's home page — `/`, following redirects, since `mkdocs serve` redirects `/` to a site served under a path — and take the text of its `<title>` element, with any HTML character references decoded. A MkDocs theme titles its home page with the site name, or with `<page title> - <site name>` where the page sets its own title, as the scaffold's does; so the page names the server whose build's site name the title equals, or ends with after ` - `. **Compare the whole name, never a substring**: one scaffold name contains the other. Where two servers' names fit, or none does, the page names none. A profile whose servers do not pair with builds — the schema's two-space `cloud`/`self-hosted` example — or whose build configs are not MkDocs configs gets nothing from this: its servers are identified by process or not at all.

Where the process and the page both name a server and they name different ones, the evidence contradicts itself, and nothing names a server.

**What the evidence decides**, at the configured port, at each pre-scan port and at each port Phase 3 walks — wherever the port answers as this docs site and no living recorded entry of another server is bound to it:

- **The selected server, in this checkout** — the evidence names the selected server, and the listener's checkout is established as this one or not established. **Re-adopt it, on every profile**: report its URL, and whether it sits off the configured port; record an entry at that port in Phase 7's shape — `requested_port` the port Phase 1 resolved, `pid` the listener's where its checkout is established as this one and otherwise none — and stop. **Never start a second copy.**
- **Another checkout, or another of this repo's servers** — the listener's checkout is established as another one, or the evidence names a server other than the selected one. Leave it running and record nothing, and name what holds the port in the Phase 6 report — another checkout by its top level. At the port being served it is a collision, which step 2 below handles; in the pre-scan and in Phase 3's walk, pass over it.
- **Nothing names a server** — no listener is named, or its command line names none, and the page names none or does not apply:
  - where `dev_servers.servers[]` holds **one** server, re-adopt it by the page alone, since it is the only candidate — exactly as for the selected server above;
  - where it holds **more than one**, report the port as answering as this docs site with its server **unconfirmed**, together with the listener's pid where the socket table named one; start nothing and record nothing — a guessed identity is exactly the entry a later `--stop` would act on — and name the way forward: stop that process by hand (its pid, where known), then re-run. Only where the selected entry's `command` carries the `{port}` token, name a second way: re-run with `--port <n>` to serve the selected server on another port. A fixed-port command has no second way, since `--port` cannot move it (Phase 1).

A re-adopted entry recorded without a pid says so, and says that `--stop` cannot end the server while it runs. A re-adoption whose listener's checkout was not established says that too: where another checkout of this repo serves that port, the reported URL shows that checkout's pages.

1. Read `<repo-root>/.dev-workflows/docs-serve.state.json` (Phase 7 writes it) and look this run's selection up by Phase 7's lookup — the server Phase 1 selected, at the port Phase 1 resolved, as overridden by `--port`. A returned entry that is living (Phase 7) is the running server — including one an earlier run's Phase 3 moved to a later port, which the lookup finds by its `requested_port`. Report its recorded URL and stop. **Never start a second server.**
2. No living entry returned (a different session started it, the state was lost, or nothing has ever run) — probe the port directly, and judge it as above. Where the evidence finds the selected server there, or names no server, what it decides governs. Otherwise the port does not answer, or it is a **collision** — a living recorded entry of another server is bound to it, it answers but not as this docs site, or the evidence names another checkout or another of this repo's servers — and, for a command carrying the `{port}` token, neither is proof the server is down: an earlier run's Phase 3 may have moved it further up and its record may be gone. That holds whether or not the configured port has come free since, because the walk takes the first free port it meets, so a copy moved past a port that was busy then can sit beyond one that is free now. So, on every profile, pre-scan the ports Phase 3 would walk (`port + 1` … `port + 20`) for such a command, judging each one that answers exactly as above. Where the evidence finds the selected server, re-adopt it (the lowest such port); failing that, where a port answers as this docs site and nothing names its server, that outcome governs at the lowest such port — re-adopted on a one-server profile, unconfirmed on a multi-server one; pass over every other port. Only where the pre-scan does neither, proceed: to Phase 4 at the configured port where it does not answer, to Phase 3 where it is a collision. A multi-server profile's common case — another of its servers on its own configured port, its record lost — is identified as that server and passed over, so only a site nothing can name still stops the run.

   **A fixed-port command gets no pre-scan.** The pre-scan looks for a copy a collision moved, and only a command carrying `{port}` can be moved: a fixed-port one binds its own port wherever it starts, so no run of this command left a copy of it above that port, and what answers there is some other server — on the schema's own two-space profile, the next space's. Pre-scanning anyway could only mislead. Where the socket table names that server's process it is passed over, which changes nothing; where nothing names it — neither `lsof` nor `ss` present, and a two-space profile has no page to tell its servers apart — it is reported as the selected server unconfirmed, the run stops, and the operator is told to stop the process holding that port, which is the other space's server. So a fixed-port command goes straight on: to Phase 4 where its port does not answer, and to Phase 3, which reports the collision, where it is one.

   **An explicit `--port <n>` runs no pre-scan.** The pre-scan infers a history — that an earlier collision moved a copy off this port — and an operator who names the port has overridden that inference. It is also what makes the unconfirmed report's `--port <n>` remedy work: a pre-scan from `<n>` would meet the same site nothing can name, and stop again. Beyond skipping the pre-scan, `--port` changes only which port is judged and served: this step and Phase 3 judge `<n>` and walk from it exactly as they judge a configured port, so a collision at `<n>` goes straight to Phase 3, and Phase 4 substitutes whichever port the run ends up serving on. `--port` on a fixed-port command never reaches this step (Phase 1).

## Phase 3 — Port collision

The selected port answers, but not as the selected server — it is not this docs site, or another of this repo's servers or another checkout holds it (Phase 2 step 2).

**A fixed-port command is never walked.** Its `command` carries no `{port}` token, so it binds its own port wherever it starts: run while that port is held, it fails with the address already in use and never answers on the port a walk chose. Report the collision instead, start nothing and record nothing:

`DOCS_SERVE_PORT_HELD: port <port> is held by <what holds it>, so <repo>'s <server> server cannot start there — its command "<command>" carries no {port} token, which means it binds that port wherever it starts and cannot be moved. Nothing was started or recorded. Stop what holds the port and re-run, or add {port} to the command where its tool takes a port argument (docs-profile-schema.md, dev_servers.servers[].command).`

`<what holds it>` is what Phase 2's tests established there — another checkout by its top level, another of this repo's servers by its space and visibility, or a process that does not answer as this docs site — followed by the listener's pid wherever the socket table named one, since that pid is what the operator stops. `<server>` is named as in Phase 1's stop.

A command carrying `{port}` is walked. Never fail on this and never reuse the port silently: walk forward from it (`port + 1`, `port + 2`, …, capped at 20 attempts) with the same probe Phase 2 used, judging each candidate the way Phase 2 judges the configured port:

- **It does not answer at all** — take it. Use that port for Phase 4, and **say so explicitly in the Phase 6 report** — a port-shifted stack (a project's ancillary services moved off their standard ports to coexist with another project's containers) is the normal case here, not the exotic one, and a silently shifted port is a URL the operator will not find.
- **A living recorded entry of another server is bound to it** — whatever its page says, as in Phase 2 — **it answers but not as this docs site, or Phase 2's evidence finds another checkout or another of this repo's servers there** — walk on, naming another checkout in the Phase 6 report by its top level.
- **Phase 2's evidence finds the selected server there, or names no server** — the selected server may already be running here, moved by an earlier run's Phase 3 whose record is gone. Phase 2's pre-scan has already re-adopted or reported such a port, unless `--port` skipped it. **Never walk past it to start a second copy**: what the evidence decides governs here exactly as at the configured port. Re-adopted, the report says it sits off the configured port, and its entry is keyed at this port with `requested_port` the port Phase 1 resolved; where nothing names a server on a profile with more than one, it is unconfirmed, and nothing is started or recorded.

Exhausting 20 attempts without a free port is reported, never guessed past.

## Phase 4 — Start

Start the selected entry's `command`, with every `{port}` in it replaced by the port this run serves on — the configured `port`, `--port <n>`, or Phase 3's shift — using the Bash tool's `run_in_background` option, from `<repo-root>` — the top level every command the profile records runs from (Phase 0), never `<repo>` where that is a site below it, and never the plugin's own directory. **Never run a command with the token unsubstituted, and never change anything in it but the token**: the substitution is the one way the port reaches the command (`docs-profile-schema.md`'s field rule), and a fixed-port command, which carries no token, runs exactly as recorded, on the port it binds itself. **Bind `0.0.0.0`, never `localhost`**: a server bound to the container's loopback is unreachable from the host, which is where the browser is. The bind address is the recorded `command`'s own concern — the token carries a port, never an address — so a `command` that only binds loopback (a bare `mkdocs serve`, whose default is `127.0.0.1:8000`, or one written `-a 127.0.0.1:{port}`) is reported as a profile defect, with the fix pointed at `/docs-workflows:docs-profile`, rather than patched here by guessing which flag the repo's generator wants.

## Phase 5 — Readiness

Poll the port this run resolved (Phase 1, as shifted by Phase 3) up to `dev_servers.readiness_timeout_seconds` (default 120 when the profile omits it), on a short interval, using the same reachability probe Phase 2 used. Stop polling the moment it answers, and read the pid of its listener from the socket table, as Phase 2 names one. **Establish that listener's checkout before anything else, as Phase 2 does.** Where it is another checkout's, the server this run started did not take the port: two checkouts started at once, both found the port free, and only one could bind. Record nothing, name that checkout in the report, and stop — a re-run finds its server there and walks past it. Otherwise proceed to Phase 6. **The listener's pid is the one Phase 7 records**, because the process holding the port is the one `--stop` must end — **never a wrapper's `$!` or the Bash tool's background-task handle**. `run_in_background` returns a task handle, not a pid, and a wrapped command (the schema's own `pnpm cloud:start`, or an npm script) leaves the port held by a child that outlives its wrapper, so stopping the wrapper would leave the site serving. Where no listener is named, or its checkout cannot be established, record the entry without a pid and say so, as Phase 2 does for a re-adopted server. A timeout is reported, not treated as failure — the started command and the elapsed wait are both in the report, so the operator can inspect a slow or wedged boot themselves rather than have a possibly-good server killed on a guess. No process holds the port yet, so there is no pid to read: record the entry without one and say so, in the same words. Once the server answers, a re-run of `/docs-serve` re-adopts it by Phase 2's evidence, with its listener's pid where the socket table names one.

## Phase 6 — Report the host-visible URL

Report the URL the operator should open:

- The selected entry's `public_base_url`, when the profile sets one, reported verbatim — recorded for exactly this reason: a command running inside a container cannot infer the host's published port mapping.
- Otherwise the in-container URL, printed together with an explicit caveat naming the likely mismatch: this repo's profile records no `public_base_url` for this server, so if you are running inside a container this address may not be the one your browser can reach — check the container's published port mapping. **Never print a URL silently that may not open.** A port-shifted stack is the normal case, not the exotic one, and guessing the mapping would be wrong more often than right.
- Where Phase 3 shifted the port, restate that here regardless of which bullet above applies: a `public_base_url` the profile recorded was recorded against the *original* port, and may no longer point at the one actually serving. Name what held the ports it passed over wherever the evidence established it — another checkout by its top level, another of this repo's servers by its space and visibility.

## Phase 7 — Record state

Write (create, or merge into) `<repo-root>/.dev-workflows/docs-serve.state.json` via Bash — an object **keyed by the port actually bound** (after any Phase 3 shift, written as a string), each entry carrying `{space, visibility, requested_port, pid, url, command, started_at}`: `space` copied from the selected `dev_servers.servers[]` entry; `visibility` the visibility of the server this run started — that entry's `dev_servers.servers[].visibility`, the field `${CLAUDE_PLUGIN_ROOT}/references/docs-profiles/docs-profile-schema.md` declares — recorded wherever the profile tags the server; `requested_port` the port Phase 1 resolved before any Phase 3 shift; `pid` the listener's, read from the socket table — by Phase 5 for a server this run started, by Phase 2 for one it re-adopted — or none where no listener was named or its checkout could not be established; `url` exactly what Phase 6 reported; and `command` the selected entry's `command` with its `{port}` replaced by the port the entry is keyed at — for a server this run started, exactly what Phase 4 ran. `space` and `visibility` are the fields the lookup below filters an entry's server by. Writing at a port replaces whatever was recorded there, and what makes that correct is the successful bind, not a lookup: a port admits one listening server, so once the server this run started — or re-adopted — holds it, anything recorded at that port describes a process that no longer does. (Phase 2's lookup could not establish it: it consults only entries recorded for the selected server.) This is what lets `--status` and `--stop` (above) work in a later session without re-deriving anything.

**The key is the port because a port holds exactly one server, and a space id does not identify one.** The profile `/docs-workflows:docs-init` writes records **one** space served **twice** — a public server and an internal one, tagged by `visibility` — so a record keyed by space made the second server started overwrite the first one's entry: the process it described kept running past `--stop`, and `--status` could no longer see it.

**The lookup** — the one rule Phase 2, `--status` and `--stop` all apply, in two steps.

1. **Filter to the selected server.** A selection made through Phase 1 — every serve run, and `--internal` in `--status` or `--stop` — names one `dev_servers.servers[]` entry. Only state entries that recorded that entry's `space` and its `visibility` (or recorded none, where it has none) are candidates — `internal` for `--internal` and `public` for its absence on a profile that tags its servers — and an entry recorded for any other server is never returned, whatever port it holds. Where two of the profile's servers share a space and neither is tagged, those fields cannot tell them apart, so a candidate must also have been started for the selection's port: its `requested_port` is *P*. A bare `--port <n>` in `--status` or `--stop` names a port, not a server, and filters nothing.
2. **Match on port.** Among the candidates, the entries for the selection's port *P* are the one keyed at *P* and any whose `requested_port` is *P* — a server Phase 3 moved off *P* because something else held it.

**A living entry is one whose pid still holds its port**: the socket table names that pid as the port's listener, as Phase 2 names one. Where neither `lsof` nor `ss` is present, its pid answering `kill -0` and its port answering as this docs site stand in for that. `kill -0` alone is never enough. Pid numbers are reused — a container restart starts them again from 1 — so the pid of a server long gone can belong to a live, unrelated process, which Phase 2 would then report as the running server and `--stop` would signal. An entry recording no pid is never living; `--status` and `--stop` judge it by its port.

Phase 2 wants the living one among what is returned; `--status` reports every one; `--stop` stops the one there is, and where there are several lists them as prose and asks, with its own picker above. Nothing here looks a server up by its space alone.

**The bound port stays the key; the filter exists because the requested port is not exclusive.** Only one live server can hold a port, so the key never has to tell two live servers apart. But a server Phase 3 moved onto another server's configured port is keyed there: a public server moved onto the internal server's port — say 8001 — or one space's server moved onto the next space's. A lookup by port alone hands the selection for that port the wrong server: Phase 2 reports it as the selected one already running, and `--stop --internal` stops the wrong process. Filtering on the server each entry recorded, before any port is matched, is what rules that out.

This file is repo-local bookkeeping, not a pipeline artefact: it is never staged and never committed. **Ignore the file itself, never its directory**: `.dev-workflows/` also holds `docs-profile.yml`, which *is* committed and which `/docs-workflows:document`, `/docs-workflows:docs-brand` and this command all read, so an ignore rule for the whole directory would silently drop the profile from the next commit that touched it. The line is `.dev-workflows/docs-serve.state.json`, and a repository `/docs-workflows:docs-init` scaffolded already carries it (`${CLAUDE_PLUGIN_ROOT}/references/docs-workflow/scaffold-tree.md` §7).
