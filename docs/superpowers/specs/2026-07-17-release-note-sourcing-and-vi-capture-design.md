- **Date:** 2026-07-17
- **Branch:** `feat/release-note-sourcing`

## Background

The prior feature gave `/release-notes` a Change Type, a type-aware Summary, and
deprecation notes, with the writer **inferring** the Change Type (or taking a
`change_type_hint`). Since then the Jira **importer was updated** to carry release-note
fields into exported VI frontmatter.

Confirmed against two real exports (`$VAULT_PATH/jira-products`):

| Field | PRODUCT-14900 | PRODUCT-14902 |
|---|---|---|
| `change_type` | `New technology support` | *absent* |
| `release_notes_category` | `Application Observability` | `Software Delivery` |
| `relevant_for_release_notes` | Yes | Yes |
| `release_versions` | Managed (344), SaaS (344) | Managed (344), SaaS (343) |

14900's release note is authored in Jira (→ `change_type` set → imported); 14902's isn't
yet (→ no `change_type`). This is the **dev-phase vs PM-phase** split: the import helps a
*dev-phase* `/release-notes` run (PM already authored the note in Jira), but not a
*PM-phase* run (the note doesn't exist in Jira yet). For the PM-phase run, the type must
come from the **authored VI in the specs dir** — which is why `release-notes-writer` must
consult it. Deprecation dates are **not** carried by the importer.

### Grounding facts

- `jira-reader` already reads the nested `<EXPORT_ROOT>/<jira_key>/<jira_key>.md` layout
  ("verified against real exports") and already parses the VI frontmatter — so the
  importer's layout change is aligned with it; **no layout fix is needed**. It must,
  however, **surface** the new fields.
- `vi-format.md` authors `relevant_for_release_notes` + `release_versions` today and
  notes that pure Jira-mirror fields are regenerated by the importer on round-trip — so
  `change_type` / `release_notes_category` / deprecation slot in as authored-then-mirrored
  fields, exactly like `release_versions`.
- Authored VIs live as `$SPECS_PATH/specifications/<KEY>-<slug>/<KEY>_<slug>.md`
  (frontmatter `issue_type: ValueIncrement`) — a filename **standardized by commit
  `633b211`**; several already carry `relevant_for_release_notes`.

## Goals

1. `release-notes-writer` sources the Change Type and `release_notes_category` from
   authored/imported data, inferring only as a last resort.
2. `/create-vi` captures those fields so PM-phase authored VIs carry them.
3. All plugin metadata (versions, marketplace.json, CHANGELOG, README, CLAUDE.md) is
   brought current — for this feature **and** the merged Change Type feature.

## Non-goals

- No change to the importer or the Jira → dynatrace-docs pipeline.
- `release_notes_category` does **not** become the `{{#context}}` label (see Decision 2).
- **Deprecation is not a structured field.** EOL/EOS dates are written directly into the
  release-notes Summary prose, not stored in frontmatter. This feature adds no structured
  deprecation capture; deprecation stays handled by the merged feature (see Decision 3).
- No new commands or agents (counts unchanged).

## Design decisions (approved)

1. **Full loop** — read-side sourcing **and** write-side capture.
2. **`release_notes_category` kept separate** — surfaced in the handoff/report (and as a
   settable draft line), but the `{{#context}}` label stays **inferred** (a Solution is a
   different grain than the doc's product-area label).
3. **Deprecation is prose, not a field** — EOL/EOS dates are written directly into the
   release-notes Summary, not stored as structured frontmatter. So this feature adds **no**
   structured deprecation capture; deprecation continues to be handled exactly as the
   merged feature does (the writer detects it, writes the Summary note, and asks for a
   still-missing EOL via the existing `deprecation_eol` gap). Nothing new here.

## A. Reader — sourcing ladder (in `release-notes-writer`)

The prior feature's **Classify** step becomes a **sourcing ladder**; inference is last:

- **`change_type`** = `change_type_hint` → **imported** VI frontmatter (via the
  `jira-reader` handoff) → **authored** specs-dir VI frontmatter (read by the command) →
  **infer**. First-available-wins (no merge).
  When **both** import and authored are present and **differ**, **import wins** (the Jira
  field of record) and the Phase 8 report records a one-line divergence note
  (non-blocking).
- **`release_notes_category`** = imported → authored → none. **Surfaced** in the handoff
  and the Phase 8 report (and as a settable draft line, parallel to `Change type:`);
  **not** the `{{#context}}` label.
- **deprecation** — **unchanged from the merged feature**. The writer still detects a
  deprecation from the VI content, writes the Summary note (EOL/EOS in the prose), and
  raises the `deprecation_eol` gap when the EOL is missing. Not a structured field; not
  sourced from frontmatter.

New writer inputs (from the command): `imported_change_type`, `imported_release_notes_category`,
`authored_vi_fields: { change_type, release_notes_category }` (any may be null).
`change_type_hint` remains the top override.

## B. Plumbing — who reads what

`jira-reader` is the agent that owns parsing the Jira-export VI frontmatter, so the
**imported** fields are surfaced through it (not read ad-hoc by the command):

- **`jira-reader`** (+ `references/handoff/jira-reader.md`): surface `change_type` and
  `release_notes_category` from the VI frontmatter as additive handoff fields (read-only;
  null when absent). It already parses this frontmatter and already reads the nested
  `<EXPORT_ROOT>/<jira_key>/<jira_key>.md` layout — this only adds two output fields.
- **`/release-notes` command**:
  - Take the **imported** `change_type` + `release_notes_category` from the `jira-reader`
    handoff (Phase 3).
  - Read the **frozen specs-draft** VI as **secondary grounding** per
    `references/vi-source-resolution.md` §5 (glob `$SPECS_PATH/specifications/<KEY>-*/<KEY>_*.md`,
    confirm `issue_type: ValueIncrement`; a missing file is a graceful skip) for its
    `change_type` / `release_notes_category` frontmatter. Per that reference the specs
    draft is never authoritative over the Jira import — which is exactly our ladder order
    (imported before authored).
  - Pass both the imported and authored fields to the writer (Phase 6 brief).
  - Add the import-vs-authored divergence note and a `Release-notes category:` line to the
    Phase 8 report/draft.

> **Scope note:** the command's existing Phase-2 worthiness check reads
> `release_versions` / `relevant_for_release_notes` directly from frontmatter *before*
> `jira-reader` runs (Phase 3), so those stay as-is. The two new fields are needed only at
> render (Phase 6), so routing them through the Phase-3 `jira-reader` handoff is clean and
> introduces no ordering problem. The **authored**-VI read stays in the command — it lives
> in the specs repo, outside `jira-reader`'s Jira-export scope.

## C. Write-side — so PM-phase VIs carry the data

All three files were touched by `633b211`; edits build on their current content (the new
`vi-format.md` frontmatter fields + "internally consistent" rule, and `create-vi`'s
`--from-vi` seeding stay intact).

- **`references/vi-format.md`**: add two optional authored frontmatter fields —
  ```yaml
  change_type: <Breaking change | New technology support | Bug fix | not applicable>   # optional
  release_notes_category: <Dynatrace Solution, e.g. Application Observability>          # optional
  ```
  Documented as authored-then-mirrored (like `release_versions`). No deprecation field —
  deprecation lives in the release-notes Summary prose, not the VI.
- **`/create-vi` command**: its release-notes-profile frontmatter step captures these two
  (bounded — folded into the existing `relevant_for_release_notes` / `release_versions`
  question).
- **`agents/vi-reviewer.md`**: validate — `change_type` ∈ the four values; if
  `relevant_for_release_notes: yes` then `change_type` is recommended (WARN if absent). No
  deprecation validation (no such field).
