# How the BRD figures and appendices branch was verified — the fixture execution runs

Branch `iv-gu/brd-figures`, shipped at `<HEAD>`. Companion to `2026-09-22-brd-figures-rulings.md`, which records why the shipped prose says what it says; this file records how it was checked, and what the check did and did not reach.

Evidence below is cited by its path in the branch's scratch workspace — `brd-figures-verify/runs/<case>/log.md` and its siblings. **That workspace is deleted with the branch**: the citations say what was looked at, not where to look now. Anything this file does not say is gone.

## 1. What was verified, and how

The deliverable on this branch is prose an agent executes — command bodies, agent system prompts, reference files. A defect in it is a false claim, a contradiction, or an instruction that cannot be followed as written. Successive reading passes and a six-area whole-branch review were run over it. The runs recorded here found things those passes walked past, because they did the one thing reading does not: they executed the text.

**The method.** An orchestrator subagent was handed one runner instruction file and one dispatch, and executed a slash command's own prose literally, phase by phase, from the working tree rather than from an installed plugin. Agent dispatches went out as general-purpose subagents whose prompt was the full body of the agent file under test, on the model its frontmatter pins. Expected results were written first, in `expected.md`, and were never shown to a run; the runner was told to log what the text made it do, and to record every place the text was ambiguous or unfollowable rather than improvising silently. Fixtures were synthetic: a small vault holding a business-requirements document with two linked images, an appendix, a PDF, one pasted image outside the document's own folder and one ambiguous wikilink; a second vault adding a `## § 7 Retention` section; and two link graphs for `/idea`, one shallow and one 23 files deep. Each run got its own scratch `SPECS_PATH` — a fresh `git init -b main` with one empty commit — so every file a run wrote could be listed, hashed, diffed and compared byte for byte against the customer's originals. No `AskUserQuestion` call was ever made: every array the command would present was logged verbatim with its options and the dispatch's scripted answer taken, and where no script covered a question the `(Recommended)` option was taken and the fact logged.

**What the runs deliberately did not execute**, each noted in the log at the phase it sits in: `specs-preflight`, `handoff-to-main`, `commit-artifacts`, the feedback / follow-ups / cost / `resume.md` tail, `impl-maintenance`, and documentation grounding (every run passed `--no-docs`). Every `require-on-main` gate and every command's own Phase 0 gates **were** executed.

**Limits, stated because this should not be taken for more than it is.** A run is one model's reading of the prose on one fixture: it shows that a reading exists which produces the observed result, not that every reading does. Where two runs over byte-identical input read the same document differently — and three did — that variance is itself the finding and is recorded below rather than averaged away. The fixtures are small, and some rules were never reached on them: no fixture has two slices, so the qualified cross-slice identifier form — the interesting case of the rule E2 audited — was never exercised at all, and E2's own log records that as a coverage gap of its fixture rather than as a finding about the text. Nothing here exercises the harness — `AskUserQuestion`'s arity was counted, never called; the git entry points were skipped by instruction; the model-routing skill was never loaded. And the runs are not a substitute for the gates: `validate-catalog.py`, `check-id-grammar.sh`, `check-docs.sh` and the mermaid gate check structure, these runs check behaviour, and neither half reaches the other's.

## 5. What execution found that reading did not

Successive reading passes and a six-area whole-branch review preceded or accompanied these runs. The classes below are what only running the text produced.

- **A stop that fires on correct input.** Run P2: `/brd-package` Phase 8 stopped `BRD_PACKAGE_DEAD_CITATION` on the schema's own example identifier, which the command inlines into part 10 of every prompt it renders — so every package with fewer than twelve code-grounding findings halted at the last step. Critical. Reading the rule and reading the schema separately, both are correct.
- **A rule whose own output the next rule forbids.** Run P3 disposed eleven of seventeen findings as agreed-but-not-actionable, and the fix for that class required a reason naming the command that fixes it — while part 9 forbids any command name and the plugin-free scan hard-stops on one and never sanitises. As specified, the fix either blocked the command or silently reverted itself. Critical. It took a run producing eleven such findings to show the state was the common path rather than an edge.
- **A loop with no exit.** Run A5: the coverage question's recommendation marker never leaves *Re-read* for a prose section the reader was handed and deliberately left without a row, so an agent told to "take the recommendation" never terminates. The array reads correctly; only executing it shows the marker never moves.
- **A recommended option that ends the run with nothing written.** Three independent runs hit it (A6, P3, P4) on `/brd-intake` Phase 1's other-file array. The first sighting was dismissed; the third reversed the dismissal. P4 logged its departure from the runner's own fallback rather than taking it silently.
- **Arithmetic that only a real fixture exposes.** Run F5: four of its seven findings were one subject — two page tallies counting different sets, a headline gloss contradicting the headline it glosses, and an option label counting a set the five-line list above it never showed. Every one of them is invisible until a number is actually computed from a graph.
- **Model variance as evidence rather than noise.** A5, A6, A7 and their re-runs read byte-identical bytes three different ways — 12, 15 and 13 requirements — and inside each pair the re-run's own read returned different wordings again, on six rows in one and seven in another. The reconciliation held every existing id and every existing row's text across all three pairs, writing none of those rewordings through. No reading of the prose could have established that; it is a property of the reconciliation under variance, and it is the single most reassuring result in this record.
- **A count the run itself got wrong, in prose beside a correct list.** Run P4's first rendering opened part 7 with *"Eleven items"* over a list of twelve. The reference names that exact class as one no membership check can see, both adversarial passes ran before the prompt existed, and the only thing that caught it was a hand count of the rendered part. - **A silent, unrecoverable write.** `/brd-intake` run against a slice key would have written `brd/source/` into a folder that holds none, renumbered rows that are never re-extracted, shadowed the parent's defect namespace, and rewritten the slice's ledger with every row `unallocated` — destroying the allocations an earlier walk recorded, with nothing short of git recovering them. Found by the whole-branch review reading run logs, graded Critical by the controller on the unrecoverable loss, and **verified live by A8**: the stop fires off `parent:`, before the consent array is composed, with nothing written and nothing asked.

**The four Criticals.** The whole-branch review graded four across six areas, and a scoped re-review confirmed all four resolved, each traced through every route its finding named. They were: the slice-intake write above; `/brd-package`'s disposition gate forbidding `fixed` on the artifacts and then, four paragraphs later, telling the run to fix them (which descends from run P3's first prose problem — the fix it bought got a table row and not a sweep); a requirement defect that makes a new round askable being withheld as waiting on the round it just opened, so round 2 opens empty, nothing closes it, and a question only the customer can settle is never asked; and `/release-notes` advancing its note boundary past what the run actually read, permanently and silently, so a repository skipped at one phase has its commits recorded as read and dropped by every later run. Only the first has been re-verified by a live run.
