# docs-auditor Handoff Format

**Core references.** A citation of the form `workflows-core:<name>` names a shared reference in the `workflows-core` plugin. Load it with `Skill(skill: "workflows-core:reference", args: "<name>")` — never by path: `${CLAUDE_PLUGIN_ROOT}` resolves to this plugin, which does not carry it.

The input and output contract for `docs-auditor`, read by the agent itself. `ia-planner` consumes this block's `surfaces[]` and `unresolved[]` verbatim; `${CLAUDE_PLUGIN_ROOT}/references/handoff/ia-planner.md` is the other half of that pair and the two agree field for field. The field names of a surface are `${CLAUDE_PLUGIN_ROOT}/references/docs-audit/backlog-format.md` §1's and the surface kinds are `${CLAUDE_PLUGIN_ROOT}/references/docs-audit/coverage-model.md` §2's; neither is restated here.

## Input

```yaml
repos:                                 # one entry per scanned repository, as code-scanner returned it
  - repo:       <repo name>
    repo_path:  <absolute path>
    status:     OK | PARTIAL | REPO_MISSING | DIRTY_TREE | REFRESH_BLOCKED | EMPTY
    prep:                              # code-scanner's prep block, carried through unchanged
      read_only:        true | false
      scanned_ref:      <ref name, e.g. "origin/main">
      ref_committed_at: <ISO-8601>
      head_divergence:  { branch: <working-tree branch>, ahead: <n>, behind: <n> }
    capability_map:                    # one entry per surface kind the scan was asked about
      - theme:          <the capability_themes[] entry, verbatim>
        classification: present | partial | absent | error
        evidence:
          - { path: <relative to repo root, at scanned_ref>, lines: [<optional>], symbols: [<optional>], note: <one line> }
        gap_summary: <present when classification is partial or absent>
        error:       <present when classification is error>

specs_inventory:                       # the caller's read of $SPECS_PATH; the `decision` and `release` kinds come from here and from nowhere else
  status:      READ | SKIPPED
  specs_path:  <absolute path, or null when SKIPPED>
  ref:         <the ref the entries were read at, or null where that tree is no git work tree>
  skip_reason: <required when status is SKIPPED, e.g. "$SPECS_PATH resolved to nothing">
  entries:
    - { kind: decision, title: "Order write path", paths: [specifications/PRD-EXAMPLE-1-orders/ard.md] }
    - { kind: release,  version: "2.4",            paths: [specifications/PRD-EXAMPLE-1-orders/release-notes.md] }

existing_surfaces:                     # optional; a --refresh run passes the surfaces already in the backlog so ids stay stable
  - { id: order-placement, kind: task, title: "Place an order" }

unresolved_themes:                     # optional; themes the CALLER's own scan rounds left unsettled with no scanner classifying them `error`
  - kind:   role                       # the surface kind the theme was asked about, so no reader parses it out of the theme text
    theme:  <the capability_themes[] entry, verbatim>
    source: <repo name, or every repo involved where the deferral was mutual>
    reason: <one line — why the caller could not settle it>
```

**`unresolved_themes[]` exists because `classification: error` is not the only way a theme goes unsettled, and this agent can see only that one.** A caller running `workflows-core:model-routing/classification` §8.5 also treats **mutual deferral** as inconclusive — two or more scanners whose `gap_summary` texts point at each other's repository — and such a theme arrives classified `present` or `partial` by every scanner that saw it, so nothing in `capability_map[]` says it was not settled. Without this field a caller would have to rewrite a scanner's `classification` to `error` to get the theme into `unresolved[]`, which would put a claim into `capability_map[]` that no scanner made — the exact substitution this contract's evidence tier forbids. Entries here are **folded into `unresolved[]` verbatim** and are never enumerated from, never judged, and never re-derived.

Refuse to run without `${CLAUDE_PLUGIN_ROOT}/references/docs-audit/coverage-model.md`, and without at least one source to enumerate from — either a `repos[]` entry carrying a `capability_map[]` or a `specs_inventory` with `status: READ`. **One of the two without the other is a run, not a refusal**: a machine with no code repositories mounted still yields the two specs-sourced kinds, and a product with no specs tree still yields the five code-derived ones. The kinds the missing source would have settled are recorded `unresolved`, never `absent`.

**`repos[]` and `coverage-model.md` are evidence inputs; `specs_inventory`, `existing_surfaces[]` and `unresolved_themes[]` are context inputs.** An unreadable evidence input is a hard stop and is never regenerated by other means; an unreadable context input degrades to absent and the degradation is recorded in `degraded[]`. The one case that crosses the two is disposed of by the refusal: degrading `specs_inventory` on a run that carries no `repos[]` leaves no source at all, so the refusal fires rather than a degradation. The agent body states both tiers in full.

**No `model_routing:` block is passed.** This agent's tier is pinned by its own frontmatter (`model: sonnet`), and nothing in the agent reads a field of that block.

**`specs_inventory.status: SKIPPED` is an ordinary input, not a failure.** A product documented from code repositories with no specs tree earns its other five kinds; the two that come from that tree are then recorded in `kinds[]` with `outcome: unresolved` and the stated `skip_reason` — never `absent`, which would assert that the product has no decisions and no releases when nothing looked.

## `volatility` — the window and the buckets, fixed here and nowhere else

Measured per surface, at the ref, over all of that surface's evidence paths in one invocation, so a commit touching several of them counts once:

```bash
git -C "<repo_path>" log <prep.scanned_ref> --since=90.days --format=%H -- <that repo's evidence paths for this surface> | wc -l
```

| Commits in the window | `volatility` |
|---|---|
| 10 or more | `high` |
| 3 to 9 | `medium` |
| 2 or fewer | `low` |
| the invocation failed | `unknown` |

**The window is one quarter**, which is long enough that a single week's burst does not decide the bucket and short enough that a rewrite two years ago does not. The thresholds sit where a surface touched more often than weekly is `high` and one touched about monthly is `medium`. They are written **once**, here, because two agents disagreeing about what `high` means is how a signal stops meaning anything — `ia-planner` reads the bucket and never re-measures.

**A `decision` or `release` surface is measured in the specs tree**, so `<repo_path>` is `specs_inventory.specs_path` and the ref is `specs_inventory.ref`; a `null` ref yields `unknown` with no invocation made, since that is the caller saying the tree is no git work tree.

**A surface with evidence in more than one repository takes the highest bucket any of them produced**, because a surface is as volatile as its most-churned part and an average would let a stable front end hide an API that changes weekly.

**`unknown` is the one value in this block outside the three `backlog-format.md` §1 fixes for `surfaces[].volatility`, and the caller owes it a resolution.** A read-only mount is not a cause — `git log` works there — so `unknown` means the invocation genuinely failed: a path not in that repository, a ref that will not resolve, or a directory that is no git work tree, which is the realistic case for a `specs_inventory` path. Because §1 admits only `high|medium|low`, `/docs-audit` writes `medium` into the file for such a surface and names the surface, with the reason, in its own report: the file stays schema-legal and the substitution is visible where a person reads it. `ia-planner` reads **this** block rather than the file, so it sees `unknown`, ranks it as `medium` and never churn-adapts on it — which is what stops a measurement nobody made from reading as a measurement.

## Output

```yaml
status: OK | PARTIAL | NO_SURFACES | INPUT_MISSING

surfaces:                              # exactly backlog-format.md §1's fields for a surface, and no others
  - id: order-placement
    kind: task                         # one of coverage-model.md §2's seven
    title: "Place an order"
    roles: [customer, admin]
    evidence:
      - { repo: example-webapp, path: src/routes/orders/new.tsx }
      - { repo: example-api,    path: app/controllers/api/v2/orders_controller.rb }
    volatility: high                   # high | medium | low | unknown

kinds:                                 # one row per surface kind, all seven, every run
  - kind:     role
    outcome:  enumerated | absent | unresolved
    surfaces: <how many surfaces of this kind this run enumerated>
    note:     <one line; required on absent and on unresolved>

unresolved:                            # a theme the scan could not settle — named, never flattened into a gap.
                                       # Every `unresolved_themes[]` entry the caller supplied appears here verbatim, beside this agent's own `error` findings.
  - kind:   role                       # the surface kind this theme was asked about, so no reader parses it out of the theme text
    theme:  <the capability_themes[] entry, verbatim>
    source: <repo name; "specs"; or several repo names, where the caller supplied a mutually-deferred theme>
    reason: <one line — the scanner's `error`, the repo status that voided its map, or the caller's own reason>

degraded:                              # context inputs that were supplied and could not be read
  - input:  specs_inventory | existing_surfaces | unresolved_themes
    reason: <one line>

notes: |
  <what a reader of the run's report needs and the blocks above do not carry: an evidence path
  that did not resolve and was dropped, a `partial` scan's gap_summary, an id disambiguated
  against another, the fact that a null-ref `specs_inventory`'s surfaces were read from the
  filesystem rather than at a ref (so drift has nothing to diff them against), the fact that no
  `role` surface was enumerated while the role theme reached `unresolved[]`, so every `roles[]`
  here is empty for want of an axis rather than for want of a role, a kind whose every surface
  was dropped for evidence that did not resolve, and — where `existing_surfaces` was not
  supplied — the fact that every id in this
  return is fresh, so the caller cannot reconcile by id.>
```

## Status codes

| Status | Meaning |
|---|---|
| `OK` | `surfaces[]` is non-empty; every one of the seven kinds settled as `enumerated` or `absent`; `unresolved[]` and `degraded[]` are both empty; every evidence path resolved at its ref; no surface carries `volatility: unknown`. |
| `PARTIAL` | `surfaces[]` is non-empty **and** at least one of these holds: `unresolved[]` is non-empty, a kind's `outcome` is `unresolved`, a context input degraded, an evidence path did not resolve and was dropped, or a surface carries `volatility: unknown`. Surfaces are still returned — a partial enumeration is worth having, and `kinds[]`, `unresolved[]` and `degraded[]` say what it is missing. **The first two conditions are both stated because neither implies the other**: a theme that errored in one repository and enumerated in another leaves `unresolved[]` non-empty with every kind `enumerated`, and a `SKIPPED` `specs_inventory` leaves two kinds `unresolved` with no `unresolved[]` entry behind them. A run matching either is `PARTIAL`. |
| `NO_SURFACES` | `surfaces[]` is empty. **This takes precedence over `PARTIAL`**, whatever else went wrong: the caller needs the one fact that there is nothing to plan, and `kinds[]` and `unresolved[]` carry whether that is because the product genuinely has none of these things or because the scan could not tell. `ia-planner` is not dispatched on this status. |
| `INPUT_MISSING` | The refusal above fired: `coverage-model.md` or every source was absent, or an evidence input could not be read. The return carries this status and the name of what was absent, **and no other block** — not an empty `surfaces[]`, not a seven-row `kinds[]`. It is distinct from `NO_SURFACES`, which is a completed enumeration that found nothing; this one is a run that never started. |

**`absent` and `unresolved` are different outcomes and a status never conflates them.** A kind is `absent` where **every source that could have settled it** looked and found none — the repositories for the five code-derived kinds, `specs_inventory` alone for `decision` and `release` — and that is a real answer with a use. A kind is `unresolved` where no such source could settle it, **or where every surface of that kind was enumerated and then dropped for evidence that did not resolve** — a source that named surfaces and whose every path then failed did tell and did not find none, so `absent` there would assert the opposite of what the evidence says. The difference is what keeps a false statement about the product out of the coverage denominator. The distinction matters most for the two specs-sourced kinds, where reading a code repository's perfectly correct `absent` as the answer would assert the product has no decision records and no releases on the strength of a source that could never have known.
