# docs-workflows — `/docs-serve`

Loaded when `/docs-serve`'s command file or docs page is read, or `docs-workflows:docs-profiles/render-verification` or `docs-workflows:toolchain-preflight`, the references its workflow-map line cites. Split out of `.claude/rules/docs-workflows.md` to keep that file under 20,000 characters; the plugin's other rules are there, and the rule that `/docs-serve` is a pure utility is in `CLAUDE.md`.

## Run state

`/docs-serve` writes no deliverable anywhere (only its own run state: the pid/port record beside the profile, one exclude line, and each start's log; what a `--build` or a dev server writes is that command's), which is why `CLAUDE.md` calls it a pure utility.

## Workflow map

```
/docs-serve          → [resolve-docs-repo] → read the profile's dev_servers block + select the server → already-running detection → port-collision fall-forward (a command carrying the {port} token only; a fixed-port one reports what holds its port and leaves nothing running), a port counting as free only where nothing answers on it and nothing is listening on it (render-verification.md §2, which defines free for the render check's pre-boot probe too; a bind that fails all the same is a collision at that port, read from the port and from the command's own log, both asked because neither sees the other's case) → start in a process group of its own (render-verification.md §2 step 2's explicit-bash form, never run_in_background), {port} substituted, once the command's tool (toolchain-preflight.md §2's) is found, with its installed dependencies where it is a package manager (render-verification.md §2 step 1) — DOCS_SERVE_NO_SERVER_TOOL otherwise, before anything starts → readiness poll, ended at once where that group is gone (the exit reported with the log's last lines, nothing recorded, never reported running — save an exit at a port something is listening on, or whose log names an address-in-use failure, which is a collision at that port and is disposed of as one), recording what answers with its listener's pid wherever that listener is in the process group it started, whatever its command line says, and otherwise only where already-running detection would re-adopt it as the selected server, its listener this checkout's (a race lost to another checkout, another of the repo's servers or a foreign process records nothing and names the winner; a port whose process the socket table does not show at all is recorded without a pid, and the report says so) → report the host-visible URL → record pid/port beside the profile, under the resolved repo's git top level's .dev-workflows/ (where the profile lives and its commands run, even for a site below that top level), keyed by port and naming the started server (its space and visibility) and the log its start wrote, which --stop deletes with the entry, a write replacing the entry takes over or deletes, and a run that records nothing deletes itself — one space served twice (public + internal) is two servers   (--status / --stop / --build are its other modes; every mode but --build first confirms it can read the socket and process tables — on Linux from /proc, which needs nothing installed, elsewhere with lsof and ps (render-verification.md §2's Portability paragraph defines each read once, for this command and /document's render check alike) — and curl and bash, which runs every call it makes on a process group, and stops without one rather than guess which process holds a port or read a group call that could not run as a gone group; a lookup made through the server selection — already-running detection, and --status / --stop --internal — filters on the recorded server before it matches a port, so a server a collision moved onto another server's configured port is never taken for it; with no record left, a server is identified by evidence, never by the port it answers on — the listener's checkout (its whole git top level, so the checkout test never takes a worktree nested in the main checkout for it; outside git, the directory or one below it) and the command line it descends from (each recorded command with its {port} replaced by the port judged and a leading cd <dir> && or VAR=value set aside as toolchain-preflight.md §2 sets them aside, every quote removed from both sides and each run of whitespace collapsed, an npx command also matched as the npm exec it becomes), or, for a listener in this checkout whose command line names no server, the home page's whole site name where the builds' names differ, never overriding the command line — the process asked before the page, so a page naming no site (a VitePress shell) never hides a server its process names: the selected server is re-adopted wherever it is found, on any profile, a server established as another checkout's is never re-adopted or recorded, and only where nothing names a server and its page names the site does a one-server profile re-adopt by page, its listener in this checkout, anything else there being reported unconfirmed; the recorded pid is the listener's, never a wrapper's, every re-adopted server records one, only a readiness timeout or a port whose process the socket table does not show records an entry without one, and it counts as living only while it still holds its port — or, where the entry records a process group still its own, while any member of that group does, whatever pid it recorded, the entry then taking that member's pid; a server it started also records its process group's id and that group's leader's start time, and --stop signals the group — a timed-out server's before it binds, too — only while the group's leader still leads it with that start time, since group ids are reused as pids are; and --stop reports stopped only once no process on the port is identified as one of the repo's servers and, where nothing is identified there at all, the port no longer answers as this site — one another checkout holds is stopped, whatever its page says — and keeps the entry of a group that still runs, or of a pid that still holds its port, after SIGKILL, so a second --stop can signal it again; --internal on a profile with a public server but no internal one stops rather than serving the public site; a timed-out server still coming up in its own group is reported as starting, and counts as running, so no serve run starts a second copy of it, and its port counts as taken, so no other server's run starts on it; on a profile whose dev_servers.concurrent is false it starts nothing while another of the repo's servers is known to be running (a living entry, a starting one, or one its own port checks identified, every other server's configured port among them); a bare --port with --status or --stop names the server bound to that port; the state file is kept out of git status through the repo's local info/exclude wherever no rule ignores it, a copy someone committed excepted, which git reports until git rm --cached; the port reaches a command only through its {port} token, never by rewriting anything else in it, so --port on a fixed-port command stops, and no pre-scan looks for a moved copy of one; a server command binds the port it is given or fails, so one that moves itself off a busy port (Vite without --strictPort) is a profile defect; a pure utility — no specs-preflight, no commit-artifacts, no review gate, no maintenance phase, because it writes no deliverable anywhere — only its own run state)
```
