## [1.2.0] — 2026-09-10

### Added — the cold-start scaffold: `/docs-init`, `/docs-brand`, `/docs-serve`

Three commands answer the question the plugin previously could not: *there are no docs and no docs repo — what should exist?* Every existing command assumed documentation already existed, and documented a delta against it.

- **`/docs-init`** scaffolds a documentation repository from nothing: a product-shaped Material for MkDocs page skeleton with a stub in every section, **two builds over one content root** (public and internal), a nav generated from frontmatter `order`, Vale with a project vocabulary seeded with the product name and the scaffold's own stub vocabulary, a CI workflow that runs both builds and the two output-level visibility gates, a `.gitignore` for the build outputs, the synced Vale packages and `/docs-serve`'s state file — **created, or merged into**: an existing `.gitignore`, such as a hosting template's, gains only the lines it lacks and never loses, reorders or rewrites one of its own, and, immediately before the commit, every path the run wrote — the branding phase's logo and stylesheet included — is tested against it: a path a project line ignores is left uncommitted, never force-added, every config reference to it is removed so the committed `mkdocs.yml` names no missing file, and both are reported — and the `.dev-workflows/docs-profile.yml` that `/document`, `/docs-brand` and `/docs-serve` read (`/release-notes` reads none). It refuses to scaffold over a repository that already carries a docs signal — an in-repo `docs-profile.yml` among them, so a profiled repository built with any generator is refused — and points at `/docs-profile` instead; it also refuses a target below a git work tree's top level — an absent one included, tested through the nearest directory up its path that exists, since a `git init` there would nest a second repository inside the first — because the profile it writes lives at a work tree's top level. It branches before it writes, verifies the scaffold builds and lints, and finishes on a **drafted** pull request it never pushes. Its lint applies **the same Vale exit criterion its CI workflow applies, over the same configuration** — it runs Vale on the repository's configuration alone, with the machine's global configuration and any `VALE_CONFIG_PATH` set aside, which is what CI's bare `vale docs/` reads on a GitHub-hosted runner, and its `vale sync` runs the same way, so the packages it installs into the repository's `styles/` are the ones the repository's `.vale.ini` names — so a local pass on the scaffold's files is the verdict CI's first run reaches on them, and the stubs pass: they raise no error-level alert against the seeded vocabulary. What can still make the two differ `scaffold-tree.md` §7 names: a scaffold path a project `.gitignore` line keeps out of the commit, a newer Vale release or synced package on the runner, and a runner of the project's own that carries a Vale configuration of its own. The source-repo set it confirms is used for that run only; no profile field records it until `/docs-audit` needs one.
- **`/docs-brand`** extracts a logo and a rough primary/accent colour pair from the product's own code — a fixed precedence over a Tailwind config, CSS custom properties, a MUI theme, a web-app manifest and SCSS/LESS variables — prints every extracted value with its file and line before applying anything, checks the pair against the WCAG 2.2 threshold pair, and copies assets into the site's `docs_dir` (`docs/assets/` on the scaffold's layout) rather than linking back into the code repo. It runs standalone, or `--inline` from `/docs-init`, which folds its diff and its contrast finding into that command's own review and pull request: a rebrand never requires re-scaffolding the site. **`--inline` never aborts the scaffold**: any stop or Cancel returns `no branding applied: <reason>` with an empty diff, and `/docs-init` continues as if `--no-brand`, recording the reason — an API or CLI product with no frontend reaches `DOCS_BRAND_NOTHING_TO_APPLY` routinely. It validates the **effective** theme, following `INHERIT`, so the inheriting `mkdocs.internal.yml` the scaffold writes is accepted rather than refused, and it writes `theme` and `extra_css` only into the config that inherits nothing — never a second theme block into the inheriting one — and the `logo`/`favicon` keys only when it applies a logo. A standalone run runs the same commit-time ignore test before it commits, so a docs repository whose `.gitignore` keeps `*.svg` or `*.css` out never receives a config naming a file its commit lacks. It brands a Material site where it sits, a monorepo's `site/` below its repository's top level included: it finds the configs through the profile's `builds[]`, whose `config` paths are relative to the top level, or, where the profile records none, in the resolved directory; follows each `INHERIT` from the directory of the config that names it; and writes the stylesheet and copies the assets under each config's own `docs_dir`, resolved against that config's directory as MkDocs resolves it, while git runs at the top level.
- **`/docs-serve`** starts, stops or checks the docs site's dev server for any profiled repo and reports a URL that actually opens from the host. It never starts a second server on a port that already answers, falls forward to the next free port on a collision and says so, and `--build` runs the profile's build command and exits. **The port reaches a server only through the `{port}` token in its recorded command**, which every run replaces with the port it serves on — the configured one, `--port <n>`, or the one a collision moved it to — and which is the only part of a command ever rewritten; the same substitution identifies a moved server by its command line. A command without the token is **fixed-port**: it binds its own port, so a collision on it is reported with what holds the port (`DOCS_SERVE_PORT_HELD`) instead of falling forward, `--port` on it stops (`DOCS_SERVE_FIXED_PORT`), and no pre-scan looks above its port for a copy nothing could have moved there. Before it starts a server it checks the command's tool, as `toolchain-preflight.md` §2 defines one. For `pnpm`, `npm` or `yarn` it also checks the dependencies installed beside the lockfile: `node_modules/`, or the `.pnp.cjs` a Yarn Plug'n'Play install keeps instead. Where either is missing it stops with `DOCS_SERVE_NO_SERVER_TOOL`, rather than wait out the readiness timeout for a server that could never start. It starts a server in a process group of its own, as `/document`'s render check boots one, and a command that exits before its port answers — `mkdocs` with a theme that is not installed, a script its package does not have — ends the readiness wait as soon as that group is gone: the exit is reported with the last lines of the command's log, and nothing is recorded, rather than the timeout being waited out and the server recorded as one that might still come up. Its pid record is **keyed by port**, because a port holds one server and the profile `/docs-init` writes serves one space twice (public and internal), and each entry names the server it started — its space, and its **visibility** where the profile tags one. A lookup made through the server selection — every serve run's already-running check, and `--status`/`--stop` with `--internal` — **filters on the recorded server before matching a port**, so a server a collision moved onto another server's configured port is never reported as that one: a public server on the internal server's port is never taken for the internal one, `--stop --internal` never stops it, and one space's server is never taken for the next space's. With no record to consult, **a server is identified by evidence, never by the port it answers on**: the process the socket table names for the port — first its checkout, the git top level of its working directory compared as a whole path, so the checkout test never takes a `git worktree` nested inside the main checkout for it (outside any git work tree, where no worktree can nest, the docs directory or any directory below it), then the command line it or a process it descends from was started with — or, for a process in this checkout whose command line names no server, where the profile's builds carry different site names, the home page's whole site name, which never overrides a server the command line names. **The process is asked before the page**: a process in this checkout started with one of the profile's commands is that server whether or not its page names the site, so a client-rendered site whose page names nothing — a VitePress dev server's shell carries an empty `<title>` — is re-adopted rather than walked past and started a second time, and whether a page names the site decides anything only where the evidence names no server; anywhere else it only helps name what holds the port. A command started through `npx` is matched by the `npm exec` command line `npx` rewrites itself to. A recorded command carrying quotes is matched too: the comparison removes every `'` and `"` from both sides and collapses each run of whitespace, since the shell strips the quotes before the server sees its arguments and the Bash tool's wrapper writes each `'` as `'"'"'`. Where one command line carries several recorded commands and they nest (`pnpm start` inside `pnpm start:internal`), the longest names the server, since a process started with a shorter one never carries the longer one's text; two unrelated commands on one command line name none. A recorded command that begins `cd <dir> &&` or with a `VAR=value` assignment is matched by what follows them, as `toolchain-preflight.md` §2 finds a command's tool: the shell consumes both, so a server's own command line carries neither, whether it was typed by hand or started by this command. **It reads which process holds a port, and that process's working directory, parents and command line, from the socket and process tables, and never guesses without them.** On Linux it reads the kernel's own tables under `/proc`: `/proc/net/tcp` and `tcp6`, and each process's `fd` links, `stat`, `cmdline` and `cwd`. They need nothing installed and no root for the user's own processes, so it runs as it is in a slim container that ships neither `lsof` nor `ss` and drops root before anything could be installed. Elsewhere it reads them with `lsof` and `ps`, which macOS ships. `render-verification.md` §2 defines each read once, and `/document`'s render check reads the tables the same way. Each read runs its utilities as `command <name>`, and the socket read's `ls` as `QUOTING_STYLE=literal command ls`, since the Bash tool's shell carries the user's aliases and exported environment: an `ls` alias carrying `-F`, `--color=always`, `-Q` or `-L`, or an exported `QUOTING_STYLE` that quotes, would leave the read naming no process for a port `lsof` and `ss` name a listener on. It stops before it probes, starts, stops or records anything where `curl` is missing, or, off Linux, `lsof` or `ps` (`DOCS_SERVE_NO_PROBE`, `DOCS_SERVE_NO_SOCKET_TOOL`, `DOCS_SERVE_NO_PS`), and prints every missing tool's message at once: without a socket table nothing can say which process holds a port, so every identity given to one would be a guess. `--build` needs none of them. A port whose process the socket table does not show — one another user runs, say — names no server, whatever its page says. A server established as another checkout's — its process named by the socket table, its working directory in another checkout — is never re-adopted or recorded, so one checkout's `--stop` never ends it. The selected server is re-adopted wherever it is found, on every profile — at the configured port, on the collision walk, and, before anything starts, on the ports a collision would have moved a `{port}`-carrying command to, whether the configured port has come free since or is still held, since a moved copy can sit beyond the first free port — and another of the repository's servers is passed over. Once the server it started answers, a process in the process group it started is that server, whatever its command line says, and is recorded as such: npm rewrites its own command line as it runs, dropping its options and the `--` before the script's, and two servers whose commands differ only by a leading `cd <dir> &&` leave the same command line behind, so no command line could say it. Anything else that answers there is recorded only where the already-running check would re-adopt it as the selected server, its listener this checkout's — the same server another run in this checkout started a moment earlier, whose record the port key then replaces; where another checkout starting at the same moment, another of the repository's servers or a foreign process won the port instead, it records nothing and names what holds it. Only where nothing names the server and its page names the site does a one-server profile re-adopt it by that page, and then only where the socket table places its process in this checkout; anywhere else — a multi-server profile, or a process the table does not show or cannot place — it is reported unconfirmed, starting nothing and naming the process to stop by hand or, where the command carries `{port}`, `--port <n>`, which runs no such pre-scan. The recorded pid is always the listener's, never a wrapper's, so `--stop` never ends a wrapper and leaves its server serving, and it reports a server stopped only once no process on its port is identified as one of the repository's servers and, where nothing there is identified at all, the port no longer answers as this docs site. Every re-adopted server is recorded with its listener's pid; an entry is recorded without one in two cases only — a server that had not answered when the readiness wait ran out, and a started server's port whose process the socket table does not show, another user's or a container's published port. A server it started is also recorded with the id of the process group it started it in and the start time of that group's leader, and `--stop` ends it through that group, wrappers and all — a timed-out server before it binds, too, so a slow server never comes up unrecorded after `--stop`, whatever its command line carries — but only while the group's leader still leads it with that start time, since a group id is reused as a pid is, and a process that takes a reused one started later; `--status` reports such a server that has not yet bound its port as starting, and gives its entry the listener's pid once a process in that group holds the port. An entry recorded without a pid and without such a group is judged by what now holds its port: where the already-running check would re-adopt it as the entry's own server, the entry takes the listener's pid, and `--stop` ends it like any other; where another checkout's server, another of the repository's servers or a process that is not this docs site holds the port, or nothing answers there, the entry is stale, and `--stop` removes it without signalling anything; only where nothing identifies what answers, and it answers as this docs site, does the entry stay without a pid, and `--stop` cannot end it and leaves it in place. A recorded pid counts as living only while the socket table still names it on its port, so a pid number reused after a container restart is never reported as the running server and never signalled. With `--status` or `--stop`, a bare `--port <n>` names the server bound to `<n>` — the entry recorded at that port, never one a collision moved off it — so `--stop --port <n>` stops that server without a prompt. On a profile that sets `dev_servers.concurrent: false`, it starts nothing while another of the repository's servers is known to be running — a living recorded entry, or one its own port checks identified, which on such a profile take in every other server's configured port — and stops with `DOCS_SERVE_NOT_CONCURRENT`, naming that server and how to stop it. The state file stays out of `git status`, a copy someone committed excepted, which git reports until `git rm --cached`: where no rule ignores it, the command appends that one path to the repository's local `.git/info/exclude`, never committed, so a clean-tree gate in the family does not meet it as an untracked file, in a repository `/docs-init` scaffolded or any other. `--internal` on a profile that tags a public server but no internal one — a `/docs-init --public-only` scaffold — stops with `DOCS_SERVE_NO_INTERNAL_BUILD` instead of serving or building the public site — under `--build`, with a message naming the missing `builds[]` entry. It writes no documentation and no artefact — the one command in this plugin that writes neither — which is why it runs no `specs-preflight`, no `commit-artifacts`, no review gate and no maintenance phase; `/docs-profile`, which writes a profile, runs none of those four either, and its page, which called it the one command here that emits no cost entry, now names `/docs-serve` beside it.

### Added — `docs-scaffold-reviewer` (D25)

A new Opus-pinned agent gates both scaffolding commands. `/docs-init` and `/docs-brand` write `mkdocs.yml`, a CI workflow, `.vale.ini`, a generated nav and theme CSS — code, reviewed as code (D17) — but the plugin's declared dependencies are `workflows-core` and `prose-style`, and `code-review` and `review-fixer` ship from `dev-workflows`, so nothing guaranteed they were installed: **a miss would have removed the gate silently rather than degraded a feature**. It was also the wrong reviewer on its merits — `code-review` carries a spec-conformance dimension and a captured test baseline, and a scaffold has neither. The fixer disposition is *orchestrator applies*, behind `workflows-core:finding-triage`, so there is no re-review cycle: the orchestrator's direct edit is the fix, applied against the same finding it answers. Its Vale dimension proves that the written `.vale.ini` is the configuration Vale reads and that it loads: it looks beside it for a `.vale`, `_vale` or `vale.ini`, which Vale would read in its place, then lints one written page from the directory holding it on the repository's configuration alone — `unset VALE_CONFIG_PATH && vale --no-global`, the form `toolchain-preflight.md` §2 gives for the scaffold's `.vale.ini`, which sets `StylesPath` — and reads a runtime error as the finding, since that run loads every style a `BasedOnStyles` line names, while `vale ls-config` exits 0 on a style that does not resolve (Vale 3.21).

That file is cited as further reading and loaded by nothing.

### Changed — the docs profile records what the scaffold produces

`docs-profile-schema.md` and `docs-profile.default.yml` gain `generator` (informational only — every invocation still goes through `commands.*`, which is what keeps the generator choice reversible), `builds[]` for a repo whose one content root renders into more than one output, `dev_servers.servers[].public_base_url` (a command inside a container cannot infer the host's published port mapping, so it reports this instead of guessing) and `dev_servers.servers[].visibility`. `dev_servers.servers[].command` may carry the literal token `{port}`: every consumer that runs the command substitutes the port it serves on and never runs the token unsubstituted, nothing else in a command is rewritten, and a command without it is fixed-port — its port is its own, and no consumer can move it. A server command that binds only loopback is a profile defect, which `/docs-serve` reports rather than patches. So is one that detaches its server (`setsid`, `nohup … &`, a trailing `&`, `docker run -d`), because both consumers that start a server track it through the process group they start it in, which `setsid` or a container takes a server out of, and `/docs-serve` records a pid only for a listener in its own checkout, which a server detached into a container is not. A foreground `docker run -p …` or `docker compose up` keeps to that rule, and the schema says `/docs-serve` cannot identify the server it starts — Docker's forwarding holds its port, not the command's process — and that such a server is stopped with Docker. `/docs-init` writes the token into both of its server commands (`mkdocs serve -f <config> -a 0.0.0.0:{port}`). `/docs-profile` writes it only in place of a literal port a detected command already carries, never inventing a flag or an argument-forwarding form, and its report lists every fixed-port server it wrote; the worked example's `pnpm cloud:start` stays fixed-port. `images.policy` becomes an enum — `in-repo` (the scaffold default) / `object-store` / `cdn` — replacing a free-text sentence, with every rule that sentence carried preserved under the policy it describes, beside `images.root`, `max_bytes`, `public_prefix` and `internal_prefix`. `dev_servers.concurrent` states what its absence means — no one-at-a-time limit, which is what `/docs-init` writes by writing no key, its two servers running side by side — and `/docs-serve` honours `false`; `dev_servers.readiness_timeout_seconds` names both of its readers, `/document`'s render check and `/docs-serve`'s readiness poll. The schema also advises recording, where the operator can, a server command whose tool keeps the command line it was given — `node_modules/.bin/<tool> …` — since `/docs-serve` identifies a server by that command line. And a server command binds the port it is given, or fails: one that moves itself to another port when its own is busy is a profile defect, like a loopback-only bind, and where a tool's command line cannot pin the port, its configuration must: VitePress passes `--strictPort`, and an Astro site, whose `astro dev` takes no such flag and moves off a busy port with one, sets Vite's `server.strictPort` under `vite` in its `astro.config` — without either, Vite takes the next free port, where nothing looks for the server and `/docs-serve` can start a second copy beside it. A tool can also detach its own server: Astro 7 does wherever it detects an AI coding agent, Claude Code among them, and the schema names the opt-out Astro documents, `ASTRO_DEV_BACKGROUND=0` ahead of the command, which keeps it in the foreground. `/docs-profile` records a detected command as it stands and adds no flag, so its report now lists every server command one of these field rules calls a defect — a loopback-only bind, a detaching command, `astro dev` without that variable among them, and a command that moves off a busy port unpinned — each with the rule it breaks and how to fix it, or its tool's configuration, by hand. Run inline from `/document`, which skips that report, it hands both lists back, the fixed-port servers and these defects, and `/document` shows them.

`frontmatter-guidelines.md` gains a **reserved-keys** section (D18): `type`, `audience`, `visibility` and `unit`, reserved by this family on any docs repo it scaffolds or writes into. `docs-frontmatter`'s ownership of the schema is unchanged.

### Changed — `/document` direct mode files its bookkeeping per docs repo (D19)

A direct-mode run takes no address, so it ordinarily resolves no PRD folder, and its cost entry went to the pending file and its feedback unfiled to the specs-repo root — both reconciling against nothing, forever, which is the problem D19 names. It now takes the same rung `/docs-init` and a standalone `/docs-brand` take: both land under `$SPECS_PATH/documentation/<docs-repo-slug>/dev-workflows/`, the slug being `workflows-core:specs-repo-git` §2.1's name for the write target the run resolved, whether or not that target is a git work tree. Every direct-mode run resolves a write target, so none parks an entry in pending any more; a run whose key does resolve a PRD folder still files under it. Keyed mode is unchanged. Pending and unfiled entries left by earlier direct-mode runs stay where they are.

### Changed — `/document`'s render check boots the server that publishes each page

Phase 6.5's dev-server smoke-check booted `dev_servers.servers[<space>]`, one server per space. The profile `/docs-init` writes records **two** servers for its one space, a public one and an internal one, so on that profile the index names no single server and an agent would have to pick: picking the public server would check every internal-only affected page on a server whose build excludes it, and picking the internal one would never boot the public build at all. The server is now chosen **per affected page** (`render-verification.md` §2). A space with one server checks every page on it, as before. A space whose two servers are tagged `public` and `internal` checks a page on the public server unless the public build excludes it (`visibility.md` §1 decides which pages those are), and then on the internal one, booting them one at a time, public first. Any other space that several servers share is skipped with its reason and falls to the manual table, since a guessed server is a false result either way. Each server's `{port}` is replaced by its configured port before it boots.

### Changed — `/document`'s build check runs every build `builds[]` records

Phase 6.5's gating build check ran `commands.per_space.<space>.build`, else `commands.build`, and the profile `/docs-init` writes records `commands.build` as the public build alone — so under that rule its internal build would never run, an internal-only page with a broken link would pass the check, and only CI would catch it on the pull request. Where the profile records `builds[]`, the check now runs **every** entry, the precedence `/docs-serve --build` uses; otherwise it runs the per-space or flat command exactly as before. Each build is recorded on its own under its `id`, so a failure names the build that failed, and `doc-fixer` is handed that build's own output. The toolchain preflight derives its tools from `builds[]` too.

### Changed — `/document`'s render check stops each server by its process group

The smoke-check recorded "the process id" of each server it booted and killed it before booting the next, without saying which process. Started the way the Bash tool starts a command, that is a wrapper shell, and an `npm` or `pnpm` script adds another: signalling either leaves the server serving, so the next server booted beside it. A server that had not bound its port when the readiness poll timed out was worse: killing its wrapper left it running, and it bound after the check had moved on, outliving the run. It now boots each server **in a process group of its own** — `bash -c 'set -m; (cd <docs_repo_path> && <command>) > <log> 2>&1 & echo $!'`, where job control makes the printed pid the id of a group the command's wrappers and children inherit — and stops it by **signalling that group**, under the same explicit `bash -c`, so job control, `$!` and `kill -- -<pgid>` are bash's whatever shell the Bash tool uses (zsh on a default macOS; `dash` refuses `set -m` without a terminal and rejects `kill -- -<pgid>`), `SIGTERM` and then `SIGKILL`, after its pages and after a readiness timeout alike. **The next server boots only once two things are confirmed**: the group is gone, and the port is quiet. A group counts as gone where `kill -0` finds no member or where every member left is a zombie: a zombie runs nothing and holds no port, and under a parent that never reaps — a container whose PID 1 is `sleep infinity`, with no init — `kill -0` alone would find the group running for good and end the check after its first server. Where the port still answers, the port's **listener** is signalled as a second stop — `/docs-serve`'s definition of one, without its checkout test (this run started the server) or its state-file test (this command keeps none). Where either still cannot be confirmed, no further server boots, the record names the port or process group left running and its command, and every page not yet checked falls to the manual table. A server job control gave no group of its own is stopped by its pid and its listener instead, and a readiness timeout on it ends the check, since nothing can tell whether it will bind late. Every read of the process or socket table (the group a boot made, its members' states, a listener and its parents) comes from `/proc` on Linux, which needs nothing installed, and from `ps` and `lsof` elsewhere (`render-verification.md` §2), each utility run as `command <name>` so an alias or shell function the Bash tool's shell carries cannot change what the read parses. A missing `lsof` alone never ends the check. A probe before each boot keeps the check from booting onto a port something else already holds, and that process is never signalled. **The readiness poll ends as soon as that group is gone**: at every interval at which its request gets no response it tests the group, and a server whose command exits before its port answers — a theme that is not installed, a configuration it cannot load, a script its package lacks — is reported with the last lines of its log, its pages fall to the manual table, and the check goes on at once, where 1.1.3's poll ran until HTTP 200 or the whole readiness timeout, 120 seconds by default, for a server that had already exited.

### Changed — a 404 in `/document`'s render check has one disposition

Two live instructions disagreed: Phase 6.5's outcomes treated a 404 on an affected page as a render defect and sent it to `doc-fixer`, while the route note said a wrong route that 404s simply leaves the page on the manual table. A 404 is now always surfaced as ❌ with its URL, the page stays on the manual table, and it is never a content failure by itself: the route is derived best-effort, so a 404 cannot tell a wrong route from a missing page — and the per-page server choice above keeps internal-only pages off the public server, the systematic source of false ones — while the build check, which runs every build that compiles an affected page, owns compile failures. It counts toward `render_smoke_check`'s `findings`, on a `RAN` row. ## [1.0.0] — 2026-09-05

### Added — the documentation half of `dev-workflows`, extracted into its own plugin

Install it with `claude plugin install docs-workflows@ihudak-plugins`. Updating the marketplace alone does **not** install it: `dev-workflows` does not declare it, because no `dev-workflows` run loads anything from it. Three commands move here from `dev-workflows` 3.26.0, and each keeps its bare name once this plugin is installed — only the namespaced form changes:

| Command | Was | Is now |
|---|---|---|
| `/document` | `/dev-workflows:document` | `/docs-workflows:document` |
| `/docs-profile` | `/dev-workflows:docs-profile` | `/docs-workflows:docs-profile` |
| `/release-notes` | `/dev-workflows:release-notes` | `/docs-workflows:release-notes` |

**Seven agents** come with them — `diff-summarizer`, `doc-location-finder`, `doc-planner`, `doc-reviewer`, `doc-writer`, `docs-style-checker` and `release-notes-writer` — dispatched as `docs-workflows:<agent>`. An agent crosses a plugin boundary for free, so every dispatch site in every plugin simply names the new namespace.

**Fourteen reference files and one bundled skill** come with them too. Twelve of the fourteen are markdown pages: `gate-ledger.md`, `repo-verification-gates.md`, `toolchain-preflight.md`, `release-note-types.md`, `finish-and-handoff.md`, the five `docs-profiles/` authoring guides, and the two `handoff/` agent contracts. The other two are data rather than prose — `default-owners.txt` and `docs-profile.default.yml` — read by `/document`, by the `docs-frontmatter` skill and by the changelog/owners hook. The `docs-frontmatter` skill ships here now; it was `dev-workflows`'s only bundled skill and that plugin now has none.

**Two hooks.** `preload-context.sh` injects specs and repo context on a `/document` or `/release-notes` prompt — it is one half of a split, `dev-workflows` keeping the half that matches `/implement`, `/epics`, `/vuln` and `/upgrade`; the two alternations are a disjoint partition of the original six, so no prompt makes both fire. `changelog-owners-reminder` moved whole rather than being duplicated, because it resolves `default-owners.txt` and `docs-profile.default.yml` under its own `${CLAUDE_PLUGIN_ROOT}` and those files are here now — left behind it would have swallowed the miss and exited 0, losing the owners check and the built-in default profile with no signal at all.

**Two declared dependencies: `workflows-core` and `prose-style`.** The first is structural — `${CLAUDE_PLUGIN_ROOT}` resolves to the *reading* plugin, so the shared reference corpus is reached through the `workflows-core:reference` loader skill rather than by path, and every command and agent here that cites one carries a preamble saying so. The second is the one **behaviour change** in the move, sanctioned as decision S12 of the split design: an unsatisfied dependency disables a plugin rather than letting it half-run, so the branches that skipped or degraded a style check when `prose-style` was absent were unreachable and are deleted. `docs-style-checker` now always runs its complementary `prose-style-checker` pass and can no longer return `NOT_CONFIGURED`; `/release-notes`'s Phase 7 style gate skips only on the user's own answer.

### Fixed — a style-check outcome no rule ever assigned

The same work found a **pre-existing** live defect, and it is worth separating from the deletion above because the deletion did not cause it. The style-check outcome mapping had two rules for a missing primary linter: `DEGRADED` when every detected rung *failed*, and `NOT_CONFIGURED` when no rung was detected **and** `prose-style` was absent. Those do not meet. A repository with no linter of its own and `prose-style` installed — the common case — landed in neither, so the `style_check` gate had no outcome to record at all. Removing the `NOT_CONFIGURED` branch did not expose the hole; it removed the last rule that mentioned the case at all, making it unavoidable. Both rules now name "detected and failed, or never detected" explicitly — the `DEGRADED` rule and the `ERROR` → `UNAVAILABLE` rule, in `/document` and in `docs-style-checker`'s own `status` definitions alike.

One consequence to know about if you read the agent's output: `complementary_linter: none` has **inverted** meaning. It used to say "no complementary pass ran; the primary carried the gate", which mapped to `RAN`. It now says "`prose-style-checker` *was* the primary", which maps to `DEGRADED`. Same token, opposite ledger consequence, in the field `/document` derives the outcome from. Nothing else consumes it.

Everything else is behaviour-preserving. This is the third increment of the marketplace split designed in `docs/superpowers/specs/2026-09-02-marketplace-split-design.md`; the first extracted `guideline-reviewers`, the second `workflows-core`. `dev-workflows` 3.27.0's changelog records the same move from its side.
