## Residue sweep — "what did this sub-project make false?"

Searched beyond the five already-fixed instances (agent description, command description, command flag line, README rows, JSON manifest descriptions) for other statements that were true before this sub-project and became false once source typing widened to `vi`, sources gained a `vi` provenance, and the write path became depth-aware. Method: grepped `RFE`, `PRODUCT`/`PRODFB`, `provenance:`, and the old flat write-path token (`Projects/<area>` / `Projects/<Products|ideas>`) across `plugins/dev-workflows/references/*.md`, `README.md`, `CLAUDE.md`, and their mgd/copilot equivalents, then read every hit in context.

**Found — `references/vi-format.md`'s `sources:` provenance enum was not widened.** Line 28 (all three repos, byte-identical): `provenance: rfe | community-post | prompt | markdown` — no `vi`. `idea-format.md`'s own `sources:` enum was correctly widened to `rfe | vi | markdown | community-post | prompt` (Task 4/8), and `create-vi.md` Phase 3 step 1 propagates the idea's `sources[]` straight into the VI frontmatter ("`sources` (propagated)," line 127) — so a VI built from a `vi`-provenance idea (the cross-product / rewrite case that is this sub-project's central worked example, §2.6–2.8 of the design) ships a `sources` entry whose `provenance: vi` value has no home in the format its own SSOT documents. `vi-reviewer.md` only checks that `sources` "carries real provenance (not the literal `idea.md` path)" — no closed-enum validation — so this is a documentation gap, not a runtime break, but it is the same class as the five already fixed: a schema widened in one file and not its downstream mirror. Present identically in canonical, mgd, and copilot.

**Noted, softer — `references/session-hygiene.md` line 108.** "the key `/create-vi` takes is the seed RFE, not the VI-ID" — the stated reason `/idea`/`/create-vi` are excluded from the rename aid. In the `vi_disposition: rewrite` case this sub-project added, the seed key **is** the VI-ID (§2.8's whole point: the same Jira key is reused). The rename-aid exclusion itself still holds either way (it is unconditional, not keyed off this rationale), so nothing breaks, but the stated reason is no longer accurate for that branch. Present identically in canonical/mgd; not checked for a copilot equivalent given the marginal severity.

**Noted, softer — `README.md`'s `/idea` write-path phrasing.** Two spots in canonical/mgd (`/idea` row, line 16; the `$VAULT_PATH` bullet, line 106) and one in copilot (line 128) still describe the destination as `$VAULT_PATH/Projects/<area>/<slug>/idea.md` — accurate when the rule was flat (pre-sub-project), ambiguous now that a source under a `Projects/Products/` grouper lands one level deeper (`Projects/Products/<grouper>/<slug>/`). `git blame`-equivalent check confirms this phrase predates the sub-project and neither of Task 9's two README-touching commits (`3dc2394`, `be14b2b`) modified it. `<area>` is generic enough that a reader could stretch it to cover the nested case, so this is reported as a candidate rather than a clear-cut break.

**Checked and clean:** agent-count enumeration (all four JSON manifests + both READMEs read "Thirty-three" / 33, set-verified against `agents/` in an earlier task and re-spot-checked here); no bare-RFE / `PRODUCT`-prefix provenance tests survive in `idea.md` or `idea-reader.md`; no file instructs reading a `Jira - <KEY>/` path for status; no path still offers the pre-sub-project "create an empty Jira workitem" text to a rewrite run (Trap 3); copilot's manifests never enumerated the agent roster to begin with (prose-summary style), so there was nothing there to go stale.
