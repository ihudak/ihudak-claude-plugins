# SpecKit harvest — spec-driven-development methodology vs. dev-workflows

Read-only research pass comparing current GitHub SpecKit (`/workspace/dev/ai-tools/github-spec-kit`,
branch `main`) against `dev-workflows`'s spec/design pipeline (`commands/{specify,design,epics}.md`,
`references/design-format.md`, `agents/{spec-reviewer,design-reviewer,readiness-reviewer}.md`), to
decide whether ~956 commits / 120 days of SpecKit churn contain anything worth folding in.

**Bottom line:** SpecKit is a standalone, offline, git-branch-per-feature CLI (`specify init`, hook
extensions, presets, multi-agent integrations) — that whole layer is out of scope by design (we're
Jira-driven, Opus-gated, and already branch/PR at the specs-repo level). Once that's set aside, most of
SpecKit's remaining conceptual machinery (`/speckit.analyze` cross-artifact check, "spec of specs"
decomposition, context-window management, constitution-driven gates) turns out to already have a
same-or-stronger equivalent in `dev-workflows` — `readiness-reviewer`/`/ready` already does a richer
joint cross-artifact audit than `/speckit.analyze`; the Jira VI→Epic hierarchy + progress-aware picker
already does automated, tracked decomposition where SpecKit needs a hand-maintained `roadmap.md`; our
EARS-based `specification-format.md` is already stricter than SpecKit's plain "system MUST" bullets.
The one **genuinely new and missing** idea is `/speckit.converge` (added ~mid-cycle, PR #3001): a
post-implementation check that traces the actual code back against spec/plan/tasks and surfaces
drift — something our pipeline has no equivalent of (`code-review`/`test-writer`/`impl-maintenance`
never reference `[Uxx]`/`[ACxx]`/`[TCxx]` IDs at all). `/speckit.clarify`'s systematic ambiguity-category
taxonomy is a second smaller, real gap. Net: 3 small-to-medium Adapt items, everything else Skip.

## Summary of the 3 Adapt items

1. **NFR/integration/terminology ambiguity-category coverage** (from `/speckit.clarify`'s 11-category
   taxonomy) → add explicit gap-categories (performance, scalability, reliability, observability,
   security/compliance, integration/external-dependency, terminology drift) to
   `references/grilling-technique.md`'s mechanics, and a matching bullet to `spec-reviewer.md`'s
   Coverage cross-stage check so a systematically-missed NFR category becomes a flagged finding, not
   just a silently-passed spec. Does not touch `specification-format.md` (internal snapshot). Effort S.
2. **Post-implementation spec/design conformance check** (from `/speckit.converge`) → the standout find.
   Add an optional check — inside `code-review.md`'s post-review phase or `impl-maintenance.md`'s
   report — that, when a `specification.md`/`design.md` is in scope, traces the shipped diff back
   against every in-scope `[Uxx]`/`[ACxx]`/`[TCxx]` and surfaces `missing`/`partial`/`contradicts`
   findings (report-only; our pipeline has no `tasks.md` to append to). Closes a real loop: today
   nothing verifies that shipped code actually satisfies what `/design` promised. Effort M.
3. **`[Uxx]`/`[ACxx]` traceability tags on risk-planner Steps** (from `tasks-template.md`'s per-story
   task IDs) → when a `design.md`/`specification.md` is in the `risk-planner` brief, ask it to annotate
   each Step with the requirement ID it implements. Makes item 2 above cheap to compute and gives
   `code-review` a traceability anchor it lacks today. Effort S.

All three are additive, small-surface edits (no new commands, no new phases, no CLI/template
scaffolding) — each could land as its own small PR if the user wants to pursue them.
