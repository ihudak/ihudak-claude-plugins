**Core references.** A citation of the form `workflows-core:<name>` names a shared reference in the `workflows-core` plugin. Load it with `Skill(skill: "workflows-core:reference", args: "<name>")` — never by path: `${CLAUDE_PLUGIN_ROOT}` resolves to this plugin, which does not carry it.

Serve the documentation site for a profiled docs repo: $ARGUMENTS

`/docs-serve` runs a profiled documentation repository's own dev server and reports a URL that actually opens from the host — on any profiled repo, not only one `/docs-workflows:docs-init` scaffolded. It reads the `dev_servers` block `/docs-workflows:docs-profile` already wrote; it never picks a generator, a port, or a start command of its own. **It writes no documentation and no artefact** — no branch, no commit, no pull request, and (see Phase 0) no `specs-preflight`. **It also runs no review gate**: D17, the family rule that every artefact-writing command passes a high-tier review before it is trusted, names `/docs-serve` as its sole exemption — precisely because there is no artefact here for a reviewer to check.

**Signature:** `/docs-serve [<docs-repo-path>] [--internal] [--stop] [--status] [--build] [--port <n>]`

## Phase 0 — Resolve

Strip every recognized flag from `$ARGUMENTS` wherever it appears — `--internal`, `--stop`, `--status`, `--build`, and `--port <n>` (consumes the token immediately following it as its numeric argument) — before reading a positional token; the flags themselves are handled in **Mode dispatch**, below. What remains is the optional `<docs-repo-path>`.

Execute **`resolve-docs-repo`** from `${CLAUDE_PLUGIN_ROOT}/references/docs-workflow/repo-resolution.md` §1 — the signal-positive form, since this command needs a docs repo that already exists, never one to create. Do not restate its ladder here; the entry point owns it. Report which rung answered, per its own hard rule — a command that quietly works in an unexpected directory is expensive to unpick afterwards.

Record the resolved absolute path as `<repo>`, and its git work-tree top level as `<repo-root>` — `git -C <repo> rev-parse --show-toplevel`, or, where `<repo>` is in no git work tree, `<repo>` itself as `cd <repo> && pwd -P` prints it. `<repo-root>` is the profile's one home (`${CLAUDE_PLUGIN_ROOT}/references/docs-profiles/docs-profile-schema.md`, **Where the profile lives**): wherever a mode below reads the profile, runs a command it records or reads and writes the state file, it does so at `<repo-root>`, the state file sitting beside the profile — also where `<repo>` is a site below that top level, such as a monorepo's `docs/`.

**No `specs-preflight`.** This is deliberate, not an omission: `/docs-serve` writes nothing into `$SPECS_PATH` — it starts a process in the resolved docs repo and reports a URL — so opening a branch discipline for a run with no artefact behind it would be ceremony. Its closest sibling is `/workflows-core:statusline`, not `/docs-workflows:document`: like that command, this one runs no `specs-preflight` and no terminal `commit-artifacts`. The only things it writes anywhere are Phase 7's pid/port record, under `<repo-root>/.dev-workflows/`, beside the profile, and — where no rule ignores that record yet — the one line naming it in the repository's local, never-committed exclude file, which keeps it out of `git status` (Phase 7) — never anything under `$SPECS_PATH`.

## Mode dispatch

Exactly one of `--status`, `--stop`, or `--build` drives this run; where more than one appears in `$ARGUMENTS`, the first encountered (left to right) wins, and the run says which of the others it ignored.

- `--status` → **`--status` mode**, below. Reports recorded state; starts nothing.
- `--stop` → **`--stop` mode**, below. Stops a recorded server; starts nothing.
- `--build` → **`--build` mode**, below. Runs the profile's build command; starts no server.
- None of the three → the default serve flow, **Phase 1** onward.

**The probe must be able to run.** Every mode but `--build` judges ports with Phase 2's reachability probe, which runs `curl`, so before `--status`, `--stop` or the serve flow does anything else, confirm that `command -v curl` exits 0. A probe that cannot run is never read as a port that answers, nor as a free one. Where curl is missing, stop:

`DOCS_SERVE_NO_PROBE: curl is not installed here (or not on PATH), and /docs-serve judges every port with it — without it a port that answers and a free one look the same, so nothing was probed, started, stopped or recorded. Install curl and re-run.`

A probe that exits 127 later in the run — curl could not run after all — stops the same way at that point, and the stop names what the run had already done: a server it started and could not poll, left running and unrecorded, or an entry it signalled but could not re-probe.

## `--status` mode

Read `<repo-root>/.dev-workflows/docs-serve.state.json` (Phase 7 writes it). Absent, or holding no entries → report `No /docs-serve state recorded for <repo>. Nothing appears to be running (a server started outside this command is invisible to --status).` and stop cleanly — an idle repo is the ordinary state, not an error.

Otherwise, for each recorded entry — one per port, the key Phase 7 writes: test whether it is living (Phase 7), and re-probe the port and URL with the same reachability check Phase 2 uses. Report, per entry: port, space (and visibility, where recorded), pid, URL, and one of *running* (living, its port answering) or *stale* (not living, or living but its port no longer answering) — a probe that cannot run gives no status at all, and stops the mode with `DOCS_SERVE_NO_PROBE` (Mode dispatch). **A living entry's page is not asked**: where the socket table names the entry's pid on its port, that is Phase 2's process evidence, and Phase 2's site test never gates it — a server whose page names no site, such as a VitePress dev server's client-rendered shell, is *running* while its process holds the port; only where neither `lsof` nor `ss` is present does living rest on the page (Phase 7). An entry recording no pid — Phase 2 and Phase 5 say when one is written — is judged by its port alone, with Phase 2's tests: *running* where the evidence names the entry's server there, whether or not its page names this docs site, or names none while the port answers as this docs site, and *stale* otherwise; it says it has no pid. A selector narrows the report to the entries **Phase 7's lookup** returns for it: `--internal` is Phase 1's own server selection for `--internal`, looked up as that server — so only entries recorded for it are reported, which on the two-server profile `/docs-workflows:docs-init` writes means those that recorded `internal` — and a bare `--port <n>` names the **bound port**: it reports the entry keyed at `<n>`, the server on that port, and never one matched by its `requested_port`. With neither given, every recorded entry is reported.

## `--stop` mode

Read the same state file. Select the entry to stop through **Phase 7's lookup**, always — never by space alone:

- A bare `--port <n>` argument names the **bound port**: the entry keyed at `<n>` is the one stopped, and no entry is ever matched by its `requested_port`. An operator naming a port means the server on it — not a server a collision moved off it, which is keyed where it now runs — and a key admits one entry, so there is no prompt.
- An `--internal` flag is Phase 1's own selection (steps 1–3, `--port` override included) for `--internal` — the same selection a serve run makes, looked up as that server and at its port. The lookup takes only the entries recorded for the selected server — on a profile that tags its servers, the ones that recorded `internal` — and among them the one bound to the port that selection resolves or moved off it by a collision. So `--stop --internal` stops the server a `--internal` serve run started, given the same `--port` where that run carried one. On the two-server profile `/docs-workflows:docs-init` writes, that is the `internal`-tagged server and never its public twin of the same space — not even a public server an earlier collision moved onto the internal server's configured port, which a lookup by port alone would have returned.
- With neither given and exactly one entry recorded, stop that one — no prompt.
- With neither given and more than one entry recorded, resolve it the same way Phase 1 step 3 resolves an ambiguous server: the state file holds one entry per running server, as many as there are ports in use, with no count fixed anywhere, so the same cap applies. Print every recorded entry as prose above the prompt — its port, its space, and its visibility where recorded — then:
  - **Three or fewer entries** — `choices: ["port <port-1> — <space-1> (Recommended)", "port <port-2> — <space-2>", "port <port-3> — <space-3>"]` (2 or 3 options, matching however many are recorded; a recorded visibility is appended to its option, e.g. `port 8001 — docs (internal)`).
  - **Four or more entries** — `choices: ["port <port-1> — <space-1> (Recommended)", "port <port-2> — <space-2>", "port <port-3> — <space-3>", "Another entry from the list above — name its port"]`.

  The typed answer is resolved against the ports just printed — never parsed out of the free text.

For the selected entry: where it is living (Phase 7), send `SIGTERM` to its pid; wait up to 5 seconds for it to exit; `SIGKILL` if it has not. **An entry that is not living is never signalled** — its process has exited, or its pid now names some other process — and goes straight to the re-probe; where its port no longer answers, report it as already stopped. **Then re-probe the port before reporting**, with Phase 2's tests: stopped means the port no longer answers as this docs site and Phase 2's evidence names none of this repo's servers there — the process first, whether or not its page names this docs site — and nothing short of that does. Where it still answers as this docs site, or the evidence still names one of this repo's servers on it — a pid recorded by an earlier version that took a wrapper for the server, or a server something restarted — say that the port still answers although the recorded process has ended or no longer holds it, name its listener's pid where the socket table names one, and **never report the server stopped**. Remove the entry from the state file either way — its pid no longer holds the port, and leaving a stale entry behind is what breaks the next `--status`. Report what was stopped, or `Nothing recorded to stop for <repo>` when the file holds no matching entry. **An entry recording no pid** — Phase 2 and Phase 5 say when one is written, a readiness timeout among them — is judged by its port instead, exactly as `--status` judges it: where `--status` would call it stale, it is removed like any other; only where it would call it running is it a live server this command cannot stop, and then `--stop` says so, with its port, and leaves the entry in place.

## `--build` mode

Run the profile's build command and exit without starting a server — this is the flag `/docs-serve` carries instead of a separate `/docs-build` command: the pipeline already gates on the profile's build (`${CLAUDE_PLUGIN_ROOT}/references/docs-profiles/docs-profile-schema.md`'s field rules — an absent build command already disables `/docs-workflows:document`'s own gating build check), and a flag is cheaper than a whole command.

Resolve the command to run, most specific first:

1. The profile's `builds[]` list (the two-build MkDocs shape `/docs-init` scaffolds): `--internal` selects the entry whose `id` (or `visibility`) is `internal`; its absence selects `public`. Where the list records the other one but not the one asked for — a `--public-only` scaffold's lone `public` build under `--internal` — stop, never building the other visibility in its place. The IDs are Phase 1's, and the messages speak of `builds[]`, which is what is missing here:

   `DOCS_SERVE_NO_INTERNAL_BUILD: <repo>'s profile records no internal build — no builds[] entry has id or visibility internal, so --build --internal has nothing to run. A /docs-init --public-only scaffold has none by design; adding one takes an mkdocs.internal.yml build config and a builds[] entry that builds it. Drop --internal to build the public site.`

   `DOCS_SERVE_NO_PUBLIC_BUILD: <repo>'s profile records no public build — no builds[] entry has id or visibility public, so --build has nothing to run without --internal. Pass --internal to build the internal one.`

   Neither id present → fall through.
2. `commands.per_space.<space>.build`, where `<space>` is Phase 1's own selection logic, applied here even though this mode starts no server — the same space still identifies which build to run.
3. `commands.build` (flat).

No candidate resolves at any of the three → stop:

`DOCS_SERVE_NO_BUILD_COMMAND: <repo>'s profile records no build command (checked builds[], commands.per_space.<space>.build, commands.build). Run /docs-workflows:docs-profile <repo> to record one, or build by hand.`

Run the resolved command via Bash, in the foreground (this mode waits for it, unlike Phase 4's server start), from `<repo-root>` (Phase 0). Report its exit code and output; a non-zero exit is reported as a failed build, never swallowed.

## Phase 1 — Read `dev_servers` and select the server

Read `<repo-root>/.dev-workflows/docs-profile.yml` (`${CLAUDE_PLUGIN_ROOT}/references/docs-profiles/docs-profile-schema.md`). The file absent, or present but carrying no `dev_servers` block, stops the run:

`DOCS_SERVE_NO_DEV_SERVER: <repo> has no dev_servers block recorded. Run /docs-workflows:docs-profile <repo> first — it detects a repo's *:start scripts and writes this block.`

`dev_servers.servers[]` is a list, one entry per server — `space`, `command`, `port`, and optionally `base_path`, `public_base_url`, and `visibility` (`docs-profile-schema.md`'s field rules). Usually that is one per servable space, but not always: the two-build profile `/docs-init` writes records **two** servers for its **one** space, a public and an internal one, told apart by `visibility` alone — which is why the state Phase 7 records is keyed by port and never by space. A space id still labels a row of step 3's picker, beside that server's port, since the servers step 3 offers carry no `visibility` to tell them apart. Select the entry this run serves:

1. Where an entry carries the declared `visibility` field (`public | internal` — it pairs a server with the `builds[]` entry of the same visibility, and the two-build MkDocs shape `/docs-init` scaffolds records one server per build, tagged to match), `--internal` selects the `internal`-tagged entry and its absence selects the `public`-tagged one. **Where the tag asked for is on no entry, stop — never serve the other visibility in its place.** Under `--internal` with no `internal`-tagged server — the profile `/docs-init --public-only` writes records exactly one server, tagged `public` — stop: `DOCS_SERVE_NO_INTERNAL_BUILD: <repo>'s profile records no internal build — no dev_servers.servers[] entry is tagged internal. A /docs-init --public-only scaffold has none by design; adding one takes an mkdocs.internal.yml build config and a dev_servers.servers[] entry tagged visibility: internal that serves it. Drop --internal to serve the public build.` Without `--internal`, on a profile whose tagged servers are all `internal`, stop the same way: `DOCS_SERVE_NO_PUBLIC_BUILD: <repo>'s profile records no public build — no dev_servers.servers[] entry is tagged public. Pass --internal to serve the internal one.` `--status --internal` and `--stop --internal`, which make this same selection, stop the same way.
2. Where no entry carries `visibility` and the list holds exactly one entry — the ordinary case for a repo with nothing to split, including a single-space profile with no two-build scaffold behind it — use it regardless of `--internal`, and say plainly that the profile records no public/internal split for this command to honour, rather than pretending `--internal` changed anything.
3. Where the list holds more than one entry and none carries `visibility`, ask — never guess, and never render an array sized to the list: `docs-profile-schema.md` fixes no upper bound on `dev_servers.servers[]` — it states the length of neither that list nor `spaces[]`, which is "required and non-empty" and nothing more — so a naive one-row-per-server array is a tool call `AskUserQuestion` rejects the moment a profile records five servers, not a long menu. This is the same shape `workflows-core:epic-picker` *The cap* exists for — a picker built from a directory listing, with no literal options for a static check to count — so resolve it the same way. Load the reference with `Skill(skill: "workflows-core:reference", args: "epic-picker")`; cited here as the authority rather than restated.

   Print every candidate `dev_servers.servers[]` entry as prose above the prompt, one line each — its `space` id and `port` — then:

   - **Three or fewer entries** — the array carries them all: `choices: ["<space-1> — port <port-1> (Recommended)", "<space-2> — port <port-2>", "<space-3> — port <port-3>"]` (2 or 3 options, matching however many are recorded; a one-entry list never reaches this rung — it resolves at step 2).
   - **Four or more entries** — the array carries the first three plus the overflow option: `choices: ["<space-1> — port <port-1> (Recommended)", "<space-2> — port <port-2>", "<space-3> — port <port-3>", "Another server from the list above — name its space and port"]`.

   The port is on every row because nothing in `docs-profile-schema.md` stops two untagged entries sharing a space id, and two rows reading the same id would be a choice the operator cannot make. The typed answer is resolved against the `space` ids and ports just printed — never parsed out of the free text (`workflows-core:epic-picker`'s closing paragraph states the same rule for its own picker). The worked two-space profile (`cloud`, `self-hosted`) reaches the three-or-fewer case: its two servers differ by space, not by visibility, so step 1 never resolves them and step 3 prints both and asks.

**The port reaches the command only through its `{port}` token.** The selected entry's `command` may carry the literal token `{port}` (`docs-profile-schema.md`'s field rule for `dev_servers.servers[].command`), and Phase 4 replaces it with the port this run serves on — the configured `port`, `--port <n>`, or Phase 3's shift. Nothing else in a command is ever rewritten. A command without the token is **fixed-port**: it binds a port of its own wherever it starts — a baked-in `-a 0.0.0.0:8000`, or a script such as the schema's `pnpm cloud:start` that names its port inside — so nothing this command does can move it. Phase 2 runs no pre-scan for it, Phase 3 never walks it (each says why), and `--port` cannot move it either.

`--port <n>`, when given, overrides the selected entry's configured `port` for this run: Phases 2 and 3 test `<n>` rather than the profile's recorded port, Phase 2 runs no pre-scan from it, and Phase 4 substitutes it for `{port}`. **On a fixed-port command, `--port <n>` stops the serve flow here**, before anything is probed, rather than start a server that binds somewhere other than `<n>`:

`DOCS_SERVE_FIXED_PORT: <repo>'s <server> server runs "<command>", which carries no {port} token — it binds its own port, so --port <n> cannot move it, and nothing was started. Drop --port to serve it on its configured port <port>, or add {port} to the command where its tool takes a port argument (docs-profile-schema.md, dev_servers.servers[].command).`

`<server>` is the selected entry's space, followed by its visibility in parentheses where the profile tags one — `docs (internal)`. `--status` and `--stop` read `--port` as a port to look up and start nothing, so this stop is the serve flow's alone.

## Phase 2 — Already-running detection

Before starting anything, test whether the selected server is already up. **A server's identity comes from evidence, never from the port it answers on.** Every port this command judges — the configured port here, each port step 2's pre-scan probes, each other server's configured port step 3 takes on a `concurrent: false` profile, and each port Phase 3 walks — is judged the same way, in this order:

- **Does it answer?** The reachability probe, `curl -s -o /dev/null --noproxy '*' --max-time 2 http://localhost:<port>/`, read by its exit code as `${CLAUDE_PLUGIN_ROOT}/references/docs-profiles/render-verification.md` §2 defines a port that answers: exit 7, a refused connection, is a port that does not answer, and it has nothing listening on it; any other code but 127 is a port that answers; 127 means curl could not run, which is no answer at all and stops the run (Mode dispatch). Every request this command makes to a port — this probe and the home-page fetch below — carries `--noproxy '*'`, for the reason that section gives: a proxy in the environment would otherwise answer for `localhost`, so a free port would read as answering, and the proxy's page as the site's.
- **Is a living recorded entry of another server bound to it?** One the state file records at that port for a server other than the selected one — an entry step 1 of Phase 7's lookup would not keep for the selection — that is living (Phase 7). That makes it another of this repo's servers, whatever its page says — typically one an earlier run's Phase 3 moved onto the selected server's configured port: the public twin of an internal server, or another space's server.
- **Which server is it?** Decided by the evidence below, and by nothing else — **the process before the page**. A process established as another checkout's is never this run's server. A listener established as this checkout's whose command line carries exactly one server's recorded command names that server **whether or not its page names this docs site**, and so, where no socket tool names a listener, do the processes whose own command lines carry exactly one server's `{port}`-carrying command, that port in the token's place, unless they are established as another checkout's: what a process was started with is evidence, and a page can name nothing at all — a VitePress dev server's client-rendered shell carries an empty `<title>` and no site name, at `/` and under its base path alike. Only the page's site name naming a *different* server can cancel the process's answer (below).
- **Does it answer as this docs site?** Asked only where the evidence names no server — **the site test never gates the evidence**. Fetch its home page — `curl -sL --noproxy '*' --max-time 10 http://localhost:<port>/`, which prints the page, `-L` following the redirect `mkdocs serve` gives `/` for a site served under a path — and test it for something that actually names this docs site (the profile's `repo.name`, or the generator's own `site_name`, whichever the repo exposes). An answer carrying no such marker is not this docs site. A marker establishes the *site* and nothing more: every server of a multi-server profile renders a page naming it, and so does the same server run from another checkout of this repo.

**The evidence.** Two kinds count, and each names at most one of `dev_servers.servers[]`:

1. **The listening process.** The *listener* on a port is the process the socket table names for it: `lsof -t -iTCP:<port> -sTCP:LISTEN`, or where `lsof` is absent, the `pid=` value in the `users:` field of `ss -ltnp 'sport = :<port>'`. Where it names several processes, the listener is the one the others descend from (walk each one's parents with `ps -o ppid= -p <pid>`); where none is, or neither tool is present, or the one present names nothing, **no listener is named**.
   - **Checkout first.** A named listener's checkout is the git top level of its working directory — `git -C /proc/<pid>/cwd rev-parse --show-toplevel` on Linux, or on macOS the same command run on the path in the `n` line of `lsof -a -p <pid> -d cwd -Fn` — and this run's checkout is `git -C <repo-root> rev-parse --show-toplevel`: the top level Phase 0 recorded, computed by the same command as the listener's so the two compare like with like — never the resolved `<repo>` itself, since a docs repo resolved at a subdirectory of a work tree (a monorepo's `docs/`) runs its servers inside that same top level. Git resolves symlinks in both paths; where a directory is in no git work tree, its top level is the directory itself, as `cd <dir> && pwd -P` prints it. **Compare the two as whole paths, never as a prefix**: a `git worktree` can sit inside another checkout's tree — nesting them under `.worktrees/` in the main checkout is a common layout — and a prefix test calls that worktree's server the main checkout's. Equal paths establish the listener as **this checkout's**; different ones establish it as **another checkout's**, whether a sibling worktree, another clone or another project; where no listener is named, or its working directory cannot be read, the checkout is **not established**.
   - **Then which server** — only for a listener established as this checkout's. Walk from the listener up through the processes it descends from, up to pid 1, reading each one's command line with `ps -o args= -p <pid>` and its parent with `ps -o ppid= -p <pid>`: a wrapper — `pnpm …:start`, an npm script, the `sh -c` or `bash -c` the Bash tool itself starts — puts the listener in a child and the recorded command on a parent. The first command line on that walk carrying any server's recorded `dev_servers.servers[].command` verbatim — with its `{port}` replaced by the port being judged, since that is the command line a server serving that port was started with; a fixed-port command is compared as recorded; and a recorded command beginning `npx <rest>` is carried, too, by a command line carrying `npm exec <rest>`, since `npx` rewrites its own command line to that as it runs — names that server. Where it carries two servers' commands — one recorded command can be a substring of another — it names none, and the walk stops there: **never pick the longer one**. A walk that reaches pid 1 without a match names none.
   - **Where no listener is named, the command line alone** — for a command carrying `{port}`, and for no other. A command carrying the token puts the port it serves on into its own command line, so its process can be found where no socket tool names one: run `ps -A -o pid=,args=` in a Bash call of its own and read which processes' command lines carry a recorded command carrying `{port}`, compared exactly as the walk compares one — with its `{port}` replaced by the port being judged. Never pipe it through a `grep` for that command: the shell running the pipe carries the command on its own command line, and would be found in its place. Where the processes found carry exactly one server's command, they name that server; two servers' commands, or none, name none, as on the walk. Establish its checkout from each such process's working directory, read as the checkout test above reads a listener's: **another checkout's** where any of them lies in another checkout, **this checkout's** where every one lies in this one, and **not established** where a directory cannot be read — the caveat below then applies. What `ps` finds may be the wrapper the Bash tool or an npm script starts rather than the process holding the port, and nothing here tells which, so a server named this way is named without a pid: re-adopted, it is recorded without one, and `--stop` cannot end it while it runs. A fixed-port command needs none of this: it is never walked to another port (Phase 3), and a second copy of it can never start on its port, because the bind fails.
2. **The page's site name** — only on a profile where it tells the servers apart: more than one server, each pairing by `visibility` with a `builds[]` entry whose `config` is an MkDocs config that sets a `site_name` (its own key, or the one its `INHERIT` parent sets), and no two of those names the same. The two-build profile `/docs-workflows:docs-init` writes is one: `<product>` and `<product> (internal)` (`${CLAUDE_PLUGIN_ROOT}/references/docs-workflow/scaffold-tree.md` §5 and §6). Take the port's home page, fetched as the site test above fetches it — `/`, with the redirect `mkdocs serve` gives it for a site served under a path followed — and the text of its `<title>` element, with any HTML character references decoded. A MkDocs theme titles its home page with the site name, or with `<page title> - <site name>` where the page sets its own title, as the scaffold's does; so the page names the server whose build's site name the title equals, or ends with after ` - `. **Compare the whole name, never a substring**: one scaffold name contains the other. Where two servers' names fit, or none does, the page names none. A profile whose servers do not pair with builds — the schema's two-space `cloud`/`self-hosted` example — or whose build configs are not MkDocs configs gets nothing from this: its servers are identified by process or not at all.

Where the process and the page both name a server and they name different ones, the evidence contradicts itself, and nothing names a server.

**What the evidence decides**, at the configured port, at each pre-scan port and at each port Phase 3 walks — wherever the port answers and no living recorded entry of another server is bound to it:

- **The selected server, in this checkout** — the evidence names the selected server, by its process whether or not its page names this docs site, or by its page, and the checkout of the process it found — the listener, or the processes the command line alone found — is established as this one or not established. **Re-adopt it, on every profile**: report its URL, and whether it sits off the configured port; record an entry at that port in Phase 7's shape — `requested_port` the port Phase 1 resolved, `pid` the listener's where its checkout is established as this one, and otherwise none, as always where no listener was named — and stop. **Never start a second copy.**
- **Another checkout, or another of this repo's servers** — the checkout of the listener, or of the processes the command line alone found, is established as another one, or the evidence names a server other than the selected one; either way, whether or not its page names this docs site. ## Phase 4 — Start

**One server at a time, where the profile says so.** Before anything starts: where `dev_servers.concurrent` is `false` — the profile's servers cannot run at once (`docs-profile-schema.md`'s field rule) — and another of this repo's servers is **known to be running**, start nothing. Known to be running means one of two things: a living entry (Phase 7) anywhere in the state file for a server other than the selected one — an entry step 1 of Phase 7's lookup would not keep for the selection — or a port this run judged, at the configured port, in the pre-scan, on the walk or at another server's configured port (Phase 2 step 3), where the evidence named another of this repo's servers. Stop:

`DOCS_SERVE_NOT_CONCURRENT: <repo>'s profile sets dev_servers.concurrent: false — its servers cannot run at once — and <other> is already running, so the <server> server was not started and nothing was recorded. Stop <other> and re-run: <how>.`

`<other>` names each such server as Phase 1 names `<server>` — its space, with its visibility in parentheses where the profile tags one — followed by its port. `<how>` is `/docs-workflows:docs-serve --stop --port <its port>` for one a living entry records, since a bare `--port` names the server bound to that port (Phase 7's lookup); one only the evidence found has no entry for `--stop` to act on, so `<how>` is its listener's pid, stopped by hand, or, where the socket table named no pid, the process holding that port. The second kind is only what this run's own judging identified. On this profile the run judges the port Phase 1 resolved and, for a command carrying `{port}`, the twenty above it, and every other server's configured port (Phase 2 step 3), so a server of this repo with no living entry is not known to it where it holds none of the ports the run judges — a collision or `--port` moved it off its configured port and past them — or where it holds one but no evidence names it, as with a fixed-port server where no socket tool names its listener and no page tells the servers apart. The stop cannot fire on either. A profile that sets `concurrent: true`, or no `concurrent` at all — `/docs-workflows:docs-init` writes none, its public and internal servers running side by side on their own ports — skips this paragraph.

Start the selected entry's `command`, with every `{port}` in it replaced by the port this run serves on — the configured `port`, `--port <n>`, or Phase 3's shift — using the Bash tool's `run_in_background` option, from `<repo-root>` — the top level every command the profile records runs from (Phase 0), never `<repo>` where that is a site below it, and never the plugin's own directory. **Never run a command with the token unsubstituted, and never change anything in it but the token**: the substitution is the one way the port reaches the command (`docs-profile-schema.md`'s field rule), and a fixed-port command, which carries no token, runs exactly as recorded, on the port it binds itself. The command keeps its server in the foreground (the schema's field rule for `dev_servers.servers[].command`): one that detaches it — `setsid`, `nohup … &`, a trailing `&`, `docker run -d` — is a profile defect, like the loopback-only bind below, because Phase 5 records a pid only for a listener in this checkout, and a server detached out of it — into a container above all — leaves `--stop` no pid to stop it by. **Bind `0.0.0.0`, never `localhost`**: a server bound to the container's loopback is unreachable from the host, which is where the browser is. The bind address is the recorded `command`'s own concern — the token carries a port, never an address — so a `command` that only binds loopback (a bare `mkdocs serve`, whose default is `127.0.0.1:8000`, or one written `-a 127.0.0.1:{port}`) is reported as a profile defect, with the fix pointed at `/docs-workflows:docs-profile`, rather than patched here by guessing which flag the repo's generator wants.

## Phase 5 — Readiness

Where no listener is named, or its checkout cannot be established, record the entry without a pid and say so, as Phase 2 does for a re-adopted server. ## Phase 7 — Record state

Write (create, or merge into) `<repo-root>/.dev-workflows/docs-serve.state.json` via Bash — an object **keyed by the port actually bound** (after any Phase 3 shift, written as a string), each entry carrying `{space, visibility, requested_port, pid, url, command, started_at}`: `space` copied from the selected `dev_servers.servers[]` entry; `visibility` the visibility of the server this run started — that entry's `dev_servers.servers[].visibility`, the field `${CLAUDE_PLUGIN_ROOT}/references/docs-profiles/docs-profile-schema.md` declares — recorded wherever the profile tags the server; `requested_port` the port Phase 1 resolved before any Phase 3 shift; `pid` the listener's, read from the socket table — by Phase 5 for a server this run started, by Phase 2 for one it re-adopted — or none where no listener was named or its checkout could not be established; `url` exactly what Phase 6 reported; and `command` the selected entry's `command` with its `{port}` replaced by the port the entry is keyed at — for a server this run started, exactly what Phase 4 ran. `space` and `visibility` are the fields the lookup below filters an entry's server by. Writing at a port replaces whatever was recorded there, and what makes that correct is the successful bind, not a lookup: a port admits one listening server, so once the server this run started — or re-adopted — holds it, anything recorded at that port describes a process that no longer does. (Phase 2's lookup could not establish it: it consults only entries recorded for the selected server.) This is what lets `--status` and `--stop` (above) work in a later session without re-deriving anything.

**The key is the port because a port holds exactly one server, and a space id does not identify one.** The profile `/docs-workflows:docs-init` writes records **one** space served **twice** — a public server and an internal one, tagged by `visibility` — so a record keyed by space made the second server started overwrite the first one's entry: the process it described kept running past `--stop`, and `--status` could no longer see it.

**The lookup** — the one rule Phase 2, `--status` and `--stop` all apply, in two steps.

1. **Filter to the selected server.** A selection made through Phase 1 — every serve run, and `--internal` in `--status` or `--stop` — names one `dev_servers.servers[]` entry. Only state entries that recorded that entry's `space` and its `visibility` (or recorded none, where it has none) are candidates — `internal` for `--internal` and `public` for its absence on a profile that tags its servers — and an entry recorded for any other server is never returned, whatever port it holds. Where two of the profile's servers share a space and neither is tagged, those fields cannot tell them apart, so a candidate must also have been started for the selection's port: its `requested_port` is *P*. A bare `--port <n>` in `--status` or `--stop` names a port, not a server, and filters nothing.
2. **Match on port.** Among the candidates, the entries for the selection's port *P* are the one keyed at *P* and any whose `requested_port` is *P* — a server Phase 3 moved off *P* because something else held it. **A bare `--port <n>` matches the key alone**: it names the bound port, so it returns the entry keyed at `<n>` — the server on that port — and never one whose `requested_port` is `<n>`, which is a server a collision moved off `<n>` and which is keyed where it runs.

**A living entry is one whose pid still holds its port**: the socket table names that pid as the port's listener, as Phase 2 names one. Where neither `lsof` nor `ss` is present, its pid answering `kill -0` and its port answering as this docs site stand in for that. `kill -0` alone is never enough. Pid numbers are reused — a container restart starts them again from 1 — so the pid of a server long gone can belong to a live, unrelated process, which Phase 2 would then report as the running server and `--stop` would signal. An entry recording no pid is never living; `--status` and `--stop` judge it by its port.

Phase 2 wants the living one among what is returned; `--status` reports every one; `--stop` stops the one there is, and where there are several — only a selection through Phase 1 can return several, since a key admits one entry — lists them as prose and asks, with its own picker above. Nothing here looks a server up by its space alone.

**The bound port stays the key; the filter exists because the requested port is not exclusive.** Only one live server can hold a port, so the key never has to tell two live servers apart. But a server Phase 3 moved onto another server's configured port is keyed there: a public server moved onto the internal server's port — say 8001 — or one space's server moved onto the next space's. A lookup by port alone hands the selection for that port the wrong server: Phase 2 reports it as the selected one already running, and `--stop --internal` stops the wrong process. Filtering on the server each entry recorded, before any port is matched, is what rules that out.

This file is repo-local bookkeeping, not a pipeline artefact: it is never staged and never committed. **Ignore the file itself, never its directory**: `.dev-workflows/` also holds `docs-profile.yml`, which *is* committed and which `/docs-workflows:document`, `/docs-workflows:docs-brand` and this command all read, so an ignore rule for the whole directory would silently drop the profile from the next commit that touched it. The line is `.dev-workflows/docs-serve.state.json`, and a repository `/docs-workflows:docs-init` scaffolded already carries it (`${CLAUDE_PLUGIN_ROOT}/references/docs-workflow/scaffold-tree.md` §7).

**The file stays out of `git status`, in a scaffolded repository or any other.** Every write of it — here, and `--stop`'s removal of an entry — first asks git whether a rule already ignores it: where `<repo-root>` is a git work tree and `git -C <repo-root> check-ignore -q --no-index .dev-workflows/docs-serve.state.json` exits 1 — no rule matches, as in a repository `/docs-workflows:docs-init` did not scaffold — append that one path, on a line of its own, to the repository's local exclude file before writing the state file:

```
(cd <repo-root> && f=$(git rev-parse --git-path info/exclude) && mkdir -p "$(dirname "$f")" && printf '\n%s\n' .dev-workflows/docs-serve.state.json >> "$f")
```

**Run it from `<repo-root>`**: the path `--git-path` prints is relative to the directory git runs in — `.git/info/exclude` at a top level, an absolute path in a linked worktree — so from any other directory it names the wrong file. That exclude file is the repository's own, shared by all its worktrees and never committed, so the line changes nothing anyone else sees — and a clean-tree gate in this family, `/docs-workflows:docs-profile`'s, `/docs-workflows:docs-brand`'s and `/docs-workflows:document`'s among them, does not meet the state file as an untracked file to stash. Exit 0 — a rule already ignores it — appends nothing, and so does any other exit, which is git failing rather than answering; the write goes ahead either way. Where `<repo-root>` is in no git work tree, there is no status to keep it out of, and nothing is appended. `--no-index` makes the test read the rules alone: a state file someone once committed would otherwise answer "not ignored" on every run and gain a line each time — and that copy is the one no rule can hide, since git reports a tracked file's changes whatever ignores it; only `git rm --cached` takes it out of the index.
